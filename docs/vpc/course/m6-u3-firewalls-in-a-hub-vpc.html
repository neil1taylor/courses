Unit 3 of Module 6

Firewalls in a hub VPC

By the end you can choose a FortiGate offering, say what the hub VPC needs around it, and find the cause when traffic through the firewall stops.

About 10 minutesNo account needed5 steps

Northgate Freight is a made-up haulier. Its security team wants one place where traffic between prod and dev is allowed, logged or refused.

The offerings and prices come from chapter 83, which cites IBM's pages. The subnets, commands, firewall output and the failover come from real runs in chapters 84, 86, 88 and 89. The review question repeats one from unit 6.2.

Step 1 · Design it

Choose the firewall

Three decisions. Pick an answer, then read the worked answer.

From NSX: the NSX gateway firewall maps roughly to a network ACL and a virtual firewall, and the distributed firewall to a security group. A FortiGate does the inspection.

Northgate wants a firewall that survives the loss of a zone, and a public entry address that moves between zones. Which offering?

Show the worked answer

The cross-zone tile is the only one with a public address range, which lets the public entry address move between zones. A floating IP cannot cross zones. At IBM's list price a pair is $0.68 an hour for the licences (2 vCPU, ATP), plus four floating IPs and a public address range per pair.

The security team also wants web filtering. The cheapest plan is ATP. What do you do?

Show the worked answer

ATP has no web or content filtering and no secure DNS filtering. UTP is listed at $0.44 per vCPU per hour at 2 vCPU, more than twice the ATP price. IBM says the licence plan cannot be changed after deployment. The server's size can change.

The tile is deployed and healthy. What must you still build before spoke traffic reaches it?

Show the worked answer

The cross-zone tile creates one route table, for the public address range, and no hub ingress table or spoke routes. It creates every network interface with IP spoofing off, and IBM says spoofing must be on when a server is the next hop of a custom route. Its security groups let in only their own members.

Step 2 · Explore the parts

The hub's subnets, one per firewall port

The tile takes four subnets per zone, one for each port, before it runs. Select a part of the drawing to see what it does and which lines of the address plan belong to it.

↑ tap any box

port1 · public

The untrusted port. It gets a floating IP.

port2 · private

The port that is the next hop for routes. Spoke traffic arrives and leaves here.

Watch for this. The tile creates this port with IP spoofing off. Switch it on, or the firewall cannot forward traffic for other addresses.

port3 · heartbeat

The subnet the two firewalls use to see each other.

Watch for this. IBM's docs and the tile disagree on the heartbeat rules, so check this port's security group if the cluster shows one member.

port4 · management

The subnet for administering a firewall. It gets a floating IP.

Step 3 · Run it

Send prod to dev through the firewall

Chapter 86 adds a route in each spoke and in the hub ingress table, so prod to dev goes to the firewall's port2, 10.10.1.4. Then a policy allows and logs it, and the same policy is changed to deny.

bash
ibmcloud is vpc-routing-table-route-create vpct-prod vpct-prod-default-rt --zone us-east-1 --destination 10.30.0.0/16 --action deliver --next-hop $FGT --name vpct-prod-to-dev-via-fgt-rt
Name          vpct-prod-to-dev-via-fgt-rt
Status        stable
Destination   10.30.0.0/16
Next hop      10.10.1.4
Zone          us-east-1

The next hop is in another VPC, the hub. The API accepted it. The chapter makes the same kind of route in dev and in the hub ingress table.

# on the FortiGate: policy 1 accepts port2 to port2 and logs it

ssh -J ubuntu@$BASTION ubuntu@$APP1 "nc -zv -w 3 $DEV 22"

client-rst is how the log records a client that closes with a reset. nc does that after it connects.

The policy action is changed from accept to deny. What does the same nc do?

Show the answer

The firewall, not the route, decides. The log shows one line for each attempt of the client.

config firewall policy
    edit 1
        set action deny
    next
end

Step 4 · Spot the fault

Why did traffic stop?

Three real faults from the lab's runs.

One. The routes and the allow policy are in place, and prod to dev times out. A packet capture on the firewall shows the SYN arriving on port2 and leaving on port2, with no reply. A capture on the dev server shows nothing arriving. What dropped it?

Show the answer

One rule fixed it: allow all outbound to 10.0.0.0/8 on the private group. The ACL was an earlier fault: until rules for 10.10.0.0/16 existed, even a connection to the firewall's own port2 timed out. In the lab the connection timed out three times, for three separate reasons: the ACL, this security group, and the missing firewall routes and policy.

Two. The active firewall is failed over with execute ha failover set 1. Traffic stops and does not come back. On the new primary the routing table shows this:

S*      0.0.0.0/0 [10/0] via 10.10.64.1, port1, 00:02:31, [1/0]
C       10.10.64.0/24 is directly connected, port1, 00:08:07
C       10.10.65.0/24 is directly connected, port2, 00:08:07

What is missing?

Show the answer

Node 2 had no route to 10.20.0.0/16 or 10.30.0.0/16. Add a second pair of routes with node 2's gateway, 10.10.65.1. The spoke routes also named node 1's port2, and packets sent there were not forwarded once node 1 was passive.

Three. An admin runs the tile's Schematics workspace a second time after the pair is up. What happens?

Show the answer

The plan removed the version_crn of the catalogue offering from each server and set IP spoofing on both port2 interfaces back to false. The apply failed with Field validation for 'CatalogOffering' failed on the 'required' tag, and the two firewall servers were gone afterwards. Chapter 88 says not to run the workspace again after the first apply.

Step 5 · Check yourself

Three questions

After a failover, what moves the hub's ingress routes to the new active firewall, and what does not move?

Show the answer

In the lab, the connector created the two hub ingress routes and the range's route again 10, 12 and 13 seconds after the command, in zone us-east-2, with FortiOS 8.0.2. The spoke routes needed a loop outside the firewall. With it running, the stream came back about 20 seconds after the failover command and about 28 seconds after the active server was stopped. Fortinet's 7.6.0 guide says a custom table does not work, and that did not hold here.

Which firewall port is the next hop for the spoke and hub routes?

Show the answer

Port2 is the private port. Port1 is untrusted and port4 is for management. Spoke routes in chapter 86 name the firewall's port2.

Review question from Unit 6.2. An ingress route table drops traffic to 10.30.0.0/16, the dev range. Does that stop dev reaching the prod VPC?

Show the answer

Everything still worked in the lab. To stop traffic from dev, the route had to match the prod address, and that also stopped shared services and the replies to connections that prod starts.
