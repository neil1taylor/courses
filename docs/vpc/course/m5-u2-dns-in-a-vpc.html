Unit 2 of Module 5

DNS in a VPC

By the end of this unit you'll know what a private zone, a permitted network and a custom resolver each do, how to choose a DNS option for a question, and why a name can resolve while the server still can't connect.

About 10 minutesNo account needed5 steps

Northgate Freight is a made-up haulier moving its vSphere estate to IBM Cloud VPC. Its servers find each other by name, and some names live in a data centre it hasn't left yet. The commands and output below are real, from a test account.

Every command and output in this unit comes from real runs in a lab account, except the review question. The vSphere comparison is only a rough match. The comparison of DNS options comes from IBM's own pages, and we didn't run it.

Step 1 · Explore the parts

A private zone, step by step

Six commands take a name from nothing to resolving in two VPCs and forwarding to a data centre. Select a part of the drawing to see what it does and which lines make it. You can also click a line.

↑ tap any box

DNS Services instance

IBM Cloud's private DNS. Its zones resolve only on IBM Cloud, and only from permitted networks.

From vSphere: the closest thing is a DNS service, but it's only a rough match.

Watch for this. You need to install a plug-in before you can use the command line: ibmcloud plugin install dns.

Private zone

A zone that only permitted VPCs can resolve. This one is vpct.internal. Outside the permitted VPCs, its names don't exist.

Resource record

One entry in the zone. Here an A record maps app.vpct.internal to an address, with a TTL of 900 seconds.

Watch for this. We meant the record to point at a network load balancer, but by then the load balancer was gone, so the run used an app server's address, 10.20.1.19.

Permitted network

A VPC that is allowed to resolve the zone. Both VPCs were added and showed ACTIVE.

Watch for this. IBM says a permitted VPC resolves the zone because its DHCP server returns 161.26.0.7 and 161.26.0.8 as the DNS servers. If DHCP is disabled on a server, you have to set those addresses by hand.

Forwarding rule

Sends queries for a zone to the upstream resolvers you list. This rule sends onprem.vpct.internal to 192.168.0.10. A default rule for * already existed.

Watch for this. The lab's on-premises network wasn't built yet, so nothing answered at that address. The test shows only that the rule exists, because no answer came back.

Custom resolver

A resolver that DNS Services runs in your VPC subnets. IBM says it is highly available by default. This one has two locations, in two subnets, and showed HEALTHY once enabled.

Watch for this. Once enabled, servers use the resolver's two addresses, 10.40.0.5 and 10.40.64.4, instead of 161.26.0.7 and 161.26.0.8.

ibmcloud dns instance-create vpct-dns standard-dns -g vpct-lab
ibmcloud dns zone-create vpct.internal -d "private zone for the vpct estate"
ibmcloud dns resource-record-create $ZONE --type A --name app --ipv4 $VIP
ibmcloud dns permitted-network-add $ZONE --vpc-crn $CRN
ibmcloud dns custom-resolver-forwarding-rule-create $RES --type zone \
  --match onprem.vpct.internal --dns-svcs 192.168.0.10 \
  --description "on-premises names"
ibmcloud dns custom-resolver-update $RES --enabled true

Resolve a name from two VPCs

Both VPCs are permitted to use the zone. Run each command in turn. The output is what the test account returned.

A:2de4450d-…        app.vpct.internal   A      900   10.20.1.19

The zone holds one record.

You run dig +short app.vpct.internal on a server in vpct-prod and on a server in vpct-shared. The two VPCs have no route between them. What comes back?

Show the answer

Both servers return the same address. Both VPCs are permitted networks of the zone, so both resolve it. You can run the commands to see.

# on vpct-prod-app-z1-01, through the bastion

dig +short app.vpct.internal
10.20.1.19

# on vpct-shared-svc-z1-01, over SSH to its floating IP

dig +short app.vpct.internal
10.20.1.19

Both VPCs returned the same address.

The shared server now calls curl http://app.vpct.internal:8080/. Does it connect?

Show the answer

No. Name resolution and reachability are separate, and no route joined the two VPCs yet. Module 6 covers ways to join them.

curl -m 4 http://app.vpct.internal:8080/
curl exit code 28

Exit code 28 is a timeout.

Step 3 · Spot the fault

After the custom resolver is switched on

Northgate's network admin enables the custom resolver in vpct-shared. The test server's security group allows DNS out only to 161.26.0.0/24. After the server renews its lease, it reports this.

$ sudo dhclient -r && sudo dhclient
$ resolvectl status | grep -E "DNS Servers|Current DNS"
Current DNS Server: 10.40.0.5
       DNS Servers: 10.40.0.5 10.40.64.4

What do lookups from this server do now?

Show the answer

They time out. The server now asks 10.40.0.5 and 10.40.64.4, and its group allows port 53 only to 161.26.0.0/24. In our lab we added outbound rules for UDP and TCP port 53 to the two subnets that hold the resolver's addresses, 10.40.0.0/24 and 10.40.64.0/24. Without them every lookup times out.

The resolver has two forwarding rules.

$ ibmcloud dns custom-resolver-forwarding-rules $RES
ID             Description               Type      Match                  Forward To
22f6b1f7-…     on-premises names         zone      onprem.vpct.internal   192.168.0.10
9118c39b-…     default forwarding rule   default   *                      161.26.0.7, 161.26.0.8

Which rule handles a lookup of www.example.com?

Show the answer

The default rule. The name matches only the * of the default rule, and IBM says the DNS Services resolvers also resolve public names that aren't in a private zone.

Where does a lookup of x.onprem.vpct.internal go?

Show the answer

To the on-premises resolver. A name under onprem.vpct.internal goes to 192.168.0.10. In our lab nothing answered yet, because we built the on-premises network later.

Step 4 · Design it

Which DNS option answers which question?

This compares four options side by side. It comes from IBM's pages, and we didn't run it.

Northgate's customers on the internet must resolve a public name, with protection in front of it. Which option?

Show the answer

Cloud Internet Services. It's a public service, and IBM lists DDoS protection, a web application firewall, rate limiting, a content delivery network and global load balancing. The lab has no public domain, so we didn't build it.

Northgate wants a name that only its own VPCs can resolve. Which option?

Show the answer

A private zone, with each VPC permitted. IBM says private zones are resolvable only on IBM Cloud, and only from explicitly permitted networks in an account.

Servers in a VPC must resolve a name that an on-premises resolver holds. Which option?

Show the answer

A custom resolver with a forwarding rule. IBM says a custom resolver also lets on-premises resolvers resolve names in the VPC.

Many VPCs in one region must all use one resolver. Which option?

Show the answer

DNS sharing. The spokes use the hub's custom resolver. Hub and spokes must be in the same region, and a spoke has one binding, so one hub.

Step 5 · Check yourself

Four questions

Review question from Unit 5.1. You update a load balancer, and the next update fails while its provisioning status reads update_pending. What do you do?

Show the answer

Wait, then run it again. A load balancer accepts one change at a time, so wait until the provisioning status reads active between updates.

IBM's page on the resolver type shows ibmcloud is vpc-create ... --dns-resolver-type delegate. What does IBM's CLI reference say?

Show the answer

Use the update command. vpc-create accepts manual and system. vpc-update accepts delegated, and --delegate-to-vpc is required. The same IBM page uses delegated in its later examples, so follow the reference.

A spoke VPC is bound to one DNS hub. Can it also bind to a second?

Show the answer

No. IBM says a spoke can have only one binding. A hub can't have a binding of its own, and the hub and spokes must be in the same region.

The same name exists in a Cloud Internet Services zone and in a private zone. Do the two services share records?

Show the answer

No. A name can exist in both, and each service answers a different audience. Cloud Internet Services answers the public, and DNS Services answers your private networks.
