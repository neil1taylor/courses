Unit 2 of Module 6

Route tables and ingress routing

By the end of this unit you'll be able to predict which route a packet takes and which of two routes wins, and you'll know why a route that says it's advertised may go nowhere.

About 10 minutesNo account needed5 steps

Northgate Freight is a made-up haulier. Its network admins have used NSX routers, and they want to control where each subnet's traffic goes and what's allowed into a VPC.

Every command and line of output in this unit comes from real runs. The review question repeats one from unit 6.1.

Step 1 · Run it

A subnet uses one route table

The lab blocks the shared VPC, 10.40.0.0/16, from the prod app subnet. Run each command in turn.

From NSX: an NSX Tier-0 or Tier-1 router maps roughly to a route table and a Transit Gateway.

bash
ibmcloud is vpc-routing-table-route-create vpct-prod vpct-prod-default-rt --zone us-east-1 --destination 10.40.0.0/16 --action drop --name vpct-prod-default-drop-shared-rt
Name          vpct-prod-default-drop-shared-rt
Action        drop
Destination   10.40.0.0/16
Priority      2
Zone          us-east-1

Priority 2 is the default when you don't set one.

ssh -J ubuntu@<bastion-floating-ip> ubuntu@<app-server> 'nc -zv -w 4 <shared-server> 22'
nc: connect to 10.40.0.14 port 22 (tcp) timed out: Operation now in progress

The subnet uses the default table, so the drop applies, and no message says why.

ibmcloud is vpc-routing-table-create vpct-prod --name vpct-prod-egress-rt
ibmcloud is subnet-update vpct-prod-app-z1 --vpc vpct-prod --rt vpct-prod-egress-rt
Name                                       vpct-prod-egress-rt
Status                                     pending
Route Direct Link Ingress                  false
Route Internet Ingress                     false
Route Transit Gateway Ingress              false
Route VPC Zones Ingress                    false

The new table has no routes.

The app subnet now uses vpct-prod-egress-rt, which has no routes. The drop route is still in the default table. Does the same test succeed?

Show the answer

Yes. A subnet uses the one table you attach. The empty custom table leaves the system routes, which carry the traffic to the Transit Gateway.

ssh -J ubuntu@<bastion-floating-ip> ubuntu@<app-server> 'nc -zv -w 4 <shared-server> 22'
Connection to 10.40.0.14 22 port [tcp/ssh] succeeded!

Watch for this: when a subnet moves to a custom table, it loses the default table's routes, such as a VPN route.

Step 2 · Predict

Two routes, one destination: priority decides

The custom table now holds two routes to 10.40.0.0/16. A smaller priority number wins.

Suppose the delegate route has priority 0 and the drop route has priority 1, as drawn. Does the connection to the shared server succeed?

Show the answer

Yes. The lab's output: Connection to 10.40.0.14 22 port [tcp/ssh] succeeded! The lower number wins, so delegate beats drop.

Now suppose you move the delegate route to priority 3 and the drop route stays at 1. What happens?

Show the answer

It times out. The lab's output: nc: connect to 10.40.0.14 port 22 (tcp) timed out: Operation now in progress The CLI also accepted a third route to the same destination, although IBM says only two deliver routes may share one.

Step 3 · Predict

An ingress table matches where traffic is going

The lab adds a table that handles traffic arriving from the Transit Gateway. A VPC can have only one table for each ingress source.

The table drops 10.30.0.0/16 and delegates 10.0.0.0/8. Can dev still reach the prod app server on port 22?

Show the answer

Yes. Dev and shared both reached the app server, and prod still reached dev: Connection to 10.20.1.31 22 port [tcp/ssh] succeeded! The destination of traffic that arrives in prod is a prod address, so a route on the dev range matches only traffic going to dev.

Now you add a drop route for the prod range 10.20.1.0/24. What stops?

Show the answer

Dev, shared, and prod's own connections to dev all stopped. All three timed out. The replies to connections that prod starts have a prod address too, so they're dropped. An ingress route can't tell one source from another, so to stop dev alone, use a network ACL rule on the source range or a security group rule.

Dev and shared must still reach one server, 10.20.1.31. How, without deleting the drop route?

Show the answer

A delegate route to that one address, at the same priority. The longer prefix beats the drop route at equal priority, and both paths worked again for that server. A second table with the same ingress flag is refused.

Step 4 · Spot the fault

Advertised, and still not in the report

Northgate's network admin wants the Transit Gateway to learn the on-premises range 192.168.0.0/24, so the admin turns the advertise flag on for the VPN route in the default table.

bash
ibmcloud is vpc-routing-table-route-update vpct-prod vpct-prod-default-rt vpct-prod-to-onprem-rt --advertise true
Name          vpct-prod-to-onprem-rt
Action        deliver
Destination   192.168.0.0/24
Advertise     true

The route says Advertise true. The next route report lists only 10.x prefixes. Why?

Show the answer

The table doesn't advertise to anywhere. A route goes out only if its flag is true and its table advertises to somewhere. Step 1 shows "advertise_routes_to":[] for the default table.

bash
ibmcloud is vpc-routing-table-update vpct-prod vpct-prod-default-rt --advertise-routes-to transit_gateway
FAILED
Error code: bad_field
Error message: The route_transit_gateway_ingress property must be set to true when transit_gateway is specified as an advertisement target
ibmcloud is vpc-routing-table-update vpct-prod vpct-prod-default-rt --transit-gateway-ingress true
FAILED
Error message: Routing table validation failed - ingress flags can not be enabled on routing table attached to a subnet

Both fixes are refused. What works?

Show the answer

A separate Transit Gateway ingress table. The lab creates vpct-prod-tgw-ingress-rt that way, with the VPN connection as the next hop and --advertise true. About 40 seconds later the report listed 192.168.0.0/24 under the prod connection. That one route tells the gateway that prod can reach the site, and sends the arriving traffic into the VPN.

Step 5 · Check yourself

Three questions

A drop route is in the default table. A subnet moves to a custom table. Does the drop still apply to it?

Show the answer

No. The connection succeeded once the subnet used the empty custom table.

You try to make a second table the Transit Gateway ingress table. What happens?

Show the answer

It's refused. The error was bad_field: routing table with RouteTransitGatewayIngress flag set to true already exists in the VPC.

Review question from Unit 6.1. A prefix filter denies 10.30.0.0/16 on the dev connection of a Transit Gateway. Who can no longer reach dev?

Show the answer

Every other connection on the gateway. A filter on one connection hides that connection's prefixes from every other connection. The lab saw prod time out against dev while shared still worked.

Remember

A subnet uses one route table at a time, and the smaller priority number wins. An ingress route matches where traffic is going. To advertise a route, put it in a separate Transit Gateway ingress table.
