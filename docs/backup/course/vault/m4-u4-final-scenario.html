Unit 4 of Module 4

Final scenario: Northgate's recovery plan

By the end you have built a recovery plan from what the course showed, answered the board's question about stolen keys, and said what stays locked after you leave.

About 20 minutesNo account needed5 steps

Northgate Freight is a made-up company. It backs up Linux files, Windows files and a SQL database with Defender Data Protect, and archives them to a Cyber Vault. Its board asks what happens if an attacker gets the backup admin's keys. You write the plan.

Every number and screen in this unit comes from real runs in our lab, with the date given each time. The unit reviews Module 4 and uses the tests from the earlier units. The vault is a Beta in us-south, with no SLA.

Step 1 · Design it

Build the recovery plan

The attack has happened and the backup cluster is gone. For each item, decide: is it in the plan, or left out? Your answers build the plan, which you will see in step 2.

Item: choose the run to download by its time, from before the attack.

Show the answer

The infected runs were archived at 11:55, after the attack at 11:54. In our lab the clean runs were 11:43 and 11:44.

Item: keep a record of the clean files and the clean database values from before an attack.

Show the answer

Every check compared the restored data with a record made earlier: a clean manifest for the files, and 100000,-108923937 for the database.

Item: replace the agent on each server with the new cluster's agent.

Show the answer

An agent trusts one cluster. A plain rpm -Uvh --force keeps the old trust and registration fails with a TLS error, so the lab removed the old package and its saved configuration first.

Item: add the vault to the new cluster with the read key, Encryption off and Archive Object Lock off.

Show the answer

Encryption is off because the archive was written without it. The lock is on the vault, and the vault enforces it, so a read-only registration does not need it.

Item: restore to the original server.

Show the answer

A retrieved group cannot restore to the original. In our lab the restores went to /v7restore/data, C:\v7restore\data and a new database labdb_v7b.

Item: treat a restore that says Succeeded as proof.

Show the answer

In an earlier test a Linux recovery reported Succeeded while hard-linked files came back empty. The check against a manifest found it.

Item: promise that the OpenShift VMs rebuild from the vault alone on a new cluster.

Show the answer

The retrieve of the VM group failed on a new cluster. The second round did not include the VMs. Say it is not proven.

Item: delete the vault when the exercise ends.

Show the answer

The vault holds locked data until the last lock ends, 15 days after the run, and it cannot be deleted before then. Step 4 returns to this.

Step 2 · Predict

The board's question

Here is the plan your answers built.

Northgate recovery plan
 1. Keep a record of the clean files and database values.
 2. Choose a run from before the attack, by its time.
 3. New cluster; replace the agent on each server.
 4. Add the vault with the read key: Encryption off, Archive Object Lock off.
 5. CloudRetrieve: search, pick the clean run, download.
 6. Restore to a new location. Check against the record.
 7. Do not promise the OpenShift VMs.
 8. Do not plan to delete the vault.

Now the board asks what an attacker can do with stolen keys.

An attacker holds the write key. Can they delete a locked version of an archive object?

Show the answer

In our lab a delete of a locked version was refused, with "Access Denied because object protected by object lock", for the write key. It was also refused for the read key, for another key on the same storage instance, and for the account owner's token from inside the VPC.

The same attacker writes a new version of an existing object with the write key. What is left?

Show the answer

On a test object in our lab, the write returned 200 and made a new version. The first version could still be read, with the original content. The latest version was now the new content, so a holder of the write key can hide the latest data. That is one reason the plan picks a run by its time and checks the result.

Step 3 · Spot the fault

The draft note to the board

Northgate's admin writes: "We tested the plan. Everything came back from the vault alone, and we can remove the vault once the test is over." Two things in it are wrong.

Is "everything came back" true?

Show the answer

In our lab, Linux (503 of 503), Windows (503 of 503) and SQL (100000 rows, checksum -108923937) came back whole. In the first round, Linux came back with 167,639 of 181,552 files, and the OpenShift VM retrieve failed on a new cluster.

Can Northgate remove the vault once the test is over?

Show the answer

The console showed one day. The vault held data chunks locked for 9 to 15 days, the last 15 days after the run. A vault that holds locked data cannot be deleted before then.

Step 4 · What stays locked

After you leave

The test is over, and the servers and clusters can go. The vault stays.

How long after the run is the earliest the vault can be deleted?

Show the answer

15 days after the run is when the newest lock ends. In the first round the same rule held the first test vault for 18 days.

What should Northgate tell its auditor about how long the data cannot be deleted?

Show the answer

The vault enforces the lock. In our lab the console and the policy said one day while the vault held data for up to 15.

Watch for this. A vault that holds locked data cannot be deleted until the last lock ends, and the console shows a shorter lock than the vault holds. Read the dates from the vault.
