Unit 1 of Module 4

The attack: every source hit

By the end of this unit you'll be able to say what the attack changed on each source, and why the vault holds two runs of every group, one clean and one infected.

About 10 minutesNo account needed5 steps

Northgate Freight is a made-up haulier. It already backs up with Defender Data Protect, and its directors want to know what happens if an attacker gets the backup admin's keys. In this module you rebuild from the vault alone, and this unit covers the attack itself.

Every number and screen in this unit comes from a real run in our lab.

Terms used. SQL checksum: a number worked out from every row of a table; it changes if any row changes.

Step 1 · Explore the parts

Three sources, two runs each

Northgate backs up three protection groups on one cluster, cohesity-dp, and archives each to the vault. At 11:54 the attack hits every source. At 11:55 the groups are archived again.

At 11:55 the three groups ran again, after the attack. What did the vault receive?

Show the answer

A second run of each group. The infected runs were archived at 11:55, and the vault then held both the clean and the infected run of each group. The clean runs were still there.

The attack changed the servers only. Did it change the clean runs already in the vault?

Show the answer

No. In our lab the clean runs from 11:43 and 11:44 are the ones restored in the next two units, and the data matched what it was before the attack.

Step 2 · Predict

What did the attack change?

At 11:54, an attacker with access to the servers overwrote the data. Before that, Northgate's backup admin had written down a clean record of every file and of the database, so there was something to compare against.

Source           What was overwritten                         What was checked
Linux /data      every file, with random bytes                ?
Windows C:\data  every file, with random bytes                ?
SQL labdb        UPDATE dbo.items SET payload = NEWID()       ?

After the attack, how many of the 503 files on each file server differed from the clean record?

Show the answer
Source           What was overwritten                         What was checked
Linux /data      every file, with random bytes                503 of 503 differ
Windows C:\data  every file, with random bytes                503 of 503 differ
SQL labdb        UPDATE dbo.items SET payload = NEWID()       checksum -426859948

The clean SQL value was 100000,-108923937 (rows, checksum). What did the attacked labdb read afterwards?

Show the answer

A different checksum. One UPDATE set the payload of every row to a new value, and the checksum changed from -108923937 to -426859948. That's the difference the rebuild has to undo.

Step 4 · Spot the fault

The newest run isn't the clean one

Northgate's backup admin has the vault open on a new cluster. She says: "Take the newest run of each group. It's the most complete." Is that the right choice?

What does the newest run hold?

Show the answer

The attacked data. The attack was at 11:54 and the infected runs were archived at 11:55. In the next unit we chose the clean runs: Linux and Windows from 11:43, SQL from 11:44.

How should the admin choose the run to download?

Show the answer

By time. The picker in the console lists the snapshots by time, and we picked the runs from before the attack. This course doesn't show the vault marking a run as infected.

Watch for this. A backup that runs after an attack archives the attacked data too. If you know the time of the attack, pick a run from before it.

Step 5 · Check yourself

Three questions

How many runs of each group did the vault hold after the attack?

Show the answer

Two. One clean run (11:43 or 11:44) and one infected run (11:55) of each of the three groups.

How many of the 503 files on the Linux and Windows servers differed after the attack?

Show the answer

503 of 503 differed on each server.

Which SQL checksum is the clean value?

Show the answer

The clean value was 100000,-108923937. The attacked database read -426859948.
