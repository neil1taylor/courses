Unit 1 of Module 2

Get access: two roles and an allow list

By the end of this unit you'll know what an account needs before it can create a Cyber Vault, what a successful list call does and doesn't prove, and how to fix a create call that says the token is malformed.

About 10 minutesNo account needed4 steps

Northgate Freight is a made-up haulier. It already backs up with Defender Data Protect, and its directors want to know what happens if an attacker gets the backup admin's keys. Northgate plans to use a Cyber Vault, and the first step is getting its IBM Cloud account into the Beta.

Everything here comes from runs in our lab. The vault is a Beta in us-south, and it has no SLA, no warranty and no support.

Terms used. IAM role: IAM is IBM Cloud's system for deciding who may do what, and a role is a named set of permissions in it. IAM token: a short-lived string that proves who you are when you call a service. Service ID: an identity in IBM Cloud for a program, not a person. HTTP 202: the answer that means a request was accepted but is not finished. HTTP 500: the answer that means the service hit an error.

Step 1 · Explore the parts

What an account needs

The Beta is closed, so IBM has to put the account on an allow list first. Then the user needs two roles, granted by name, and a role on the storage instance.

Which role lets the user create a vault?

Show the answer

Cyber Vault Manager. The Reader role lists vaults, and the Manager role creates them.

Northgate's backup admin already has the "all IAM services" admin policy. Is that enough?

Show the answer

No. In our lab the "all IAM services" policy didn't include the two roles. We granted them with ibmcloud iam user-policy-create and waited about 20 seconds before the next call. The user also needs Editor or Administrator on the COS instance.

An account on Basic support can't open the onboarding case. Our notes don't record which route put our account on the list, only that access was missing at first and then present.

Step 2 · Predict

What a successful list call proves

Northgate's backup admin has the Reader role and lists the vaults with an API call. This is what we saw in the lab.

When                        Result
Before Reader role        HTTP 403, not authorized to list
After Reader role         HTTP 200, count 0, no vaults
One create, later         HTTP 202, then active 30 s later

The list call returns HTTP 200 with no vaults. What does that prove?

Show the answer

Only that the role works. The list returned 200 after we granted the Reader role, and the same day six creates failed.

What's the only real check that an account has access?

Show the answer

A create call. In the lab we made one vault with the shortest lock and no data, and deleted it straight away. It was active after about 30 seconds. The delete left two keys behind, which we deleted by hand. A Cyber Vault page in the console, or an email from IBM, is a weaker sign, and we didn't test either as a check.

Step 3 · Spot the fault

Fix a create that says the token is malformed

Northgate's backup admin has both roles, and the account is on the allow list. She makes a token with the CLI and calls create, and the call fails. Can you see why?

TOK=$(ibmcloud iam oauth-tokens --output json | jq -r .iam_token)
curl -X POST .../v1/cyber_vaults -H "Authorization: Bearer $TOK" ...

HTTP 500
... token is malformed: tokenstring should not contain 'bearer ' ...

What's wrong?

Show the answer

The token still has Bearer in front. The CLI prints it that way, so remove it with sed 's/^Bearer //' before you build the header. We hit this in our lab.

The call failed. What did it leave behind?

Show the answer

Nothing. A list call afterwards returned 200 with no vaults, and the instance had only the key it had before. A vault that goes to failed is different, because it leaves keys behind (unit 2.2).

Watch for this. The error says "token is malformed" and comes with HTTP 500, which looks like a service fault. In our lab the cause was the extra word in our own header, so check that first.

Step 4 · Check yourself

Three questions

Which role creates vaults?

Show the answer

Cyber Vault Manager. Reader lists and Manager creates. In our lab the admin policy for all IAM services didn't include either.

A list call returns HTTP 200 and no vaults. What do you know?

Show the answer

Only that the Reader role works. In our lab the create was the check that showed access.

A create returns HTTP 500 and "token is malformed". What do you check first?

Show the answer

The prefix. A doubled prefix gives "Bearer Bearer", and the sed command removes it.

Remember

Access takes three things. IBM puts the account on the allow list, the user holds the Reader and Manager roles, and the user has Editor or Administrator on the COS instance. Only a create proves the account is on the allow list. Strip "Bearer " from the token before you use it.
