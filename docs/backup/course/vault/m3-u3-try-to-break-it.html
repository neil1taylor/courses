Unit 3 of Module 3

Try to break it

By the end of this unit you'll be able to say what each key, and the account owner, could and couldn't do to locked data in the vault: delete it, shorten its lock, or overwrite it.

About 10 minutesNo account needed5 steps

Northgate Freight is a made-up haulier. Its directors want to know what happens if an attacker gets the backup admin's keys. In this unit you see what we tried in our lab with each key, and what the vault did.

Every result comes from real tests in our lab. Vault names, hosts and keys are made-up or placeholders, because we changed the real values.

Terms used. GET, PUT, DELETE and HEAD: requests to storage. GET reads an object, PUT writes one, DELETE removes one, and HEAD asks about an object without reading it. Object key: the name an object is stored under. It isn't a secret key.

Step 1 · Explore the parts

Four holders, one locked vault

The vault gives you two keys, a write key and a read key. We also tried a third key, made for the same storage instance but not for the vault, and the account owner's own token from inside the allowed network.

Which key could read the lock date of an object?

Show the answer

The read key. The write key could list, read and write with a lock, but it couldn't read the lock.

Which key could write a new object with a lock?

Show the answer

The write key. It wrote with a lock and got HTTP 200. The read key got 403 on a write.

Step 2 · Predict

Try to delete a locked version

We tried to delete one real data chunk and the real archive_metadata object, both locked. Each of the four holders sent a delete for one version. How many do you think got through?

DELETE /<OBJECT_KEY>?versionId=<VERSION_ID>

holder                    result
write key                 ?
read key                  ?
instance HMAC key         ?
owner token, in the VPC   ?

How many of the four holders deleted the version?

Show the answerAll four were refused.
holder                    result
write key                 403 Access Denied because object protected by object lock
read key                  403 Access Denied
instance HMAC key         403 Access Denied (it could not even list)
owner token, in the VPC   403 on GET, HEAD and DELETE

Both objects still answered HEAD 200 afterwards. The instance HMAC key was the strongest key we had, because an account-owner HMAC key doesn't exist in our account.

Same delete with the write key, now with the header x-amz-bypass-governance-retention: true. What happened?

Show the answer

403 with the same text. The lock is COMPLIANCE, so the bypass header for GOVERNANCE locks doesn't apply.

Step 3 · Run it

Shorten the lock, then overwrite

We made two more attempts with the write key in our lab. The first tries to change the lock, and the second writes new content over an old key. For the overwrite we used a test object, probe/p1.txt, rather than a real archive object.

PUT /<OBJECT_KEY>?retention&versionId=<VERSION_ID>
    COMPLIANCE until 18:00 today                    write key
    GOVERNANCE plus the bypass header               write key
PUT /probe/p1.txt        other content              write key

What happened to the two tries to shorten the lock?

Show the answer

Both got 403 "protected by object lock", on both real objects and on the probe. At bucket level, a change to the default retention and a change of versioning to Suspended also got 403, and the configuration hadn't changed afterwards.

The write key writes new content to the key probe/p1.txt, which already holds locked content. What does the vault do?

Show the answerAccepted as a new version.
PUT probe/p1.txt other content   -> 200, new version id
list                             -> two versions
GET ?versionId=<FIRST>           -> the original content (SHA-256 prefix 44e743c48cb20203)
latest version                   -> the new content

That's how a versioned bucket works: each write, including each backup, adds a version, and the lock keeps every earlier one. So someone with the write key could add a version on top, but couldn't remove or change what was already there. We tried this on a test object, not on a real archive object.

Step 4 · Spot the fault

Three statements for the directors

Northgate's IT manager has drafted a note for the directors with three statements in it. Each one needs correcting. For each, pick what our tests showed.

"The account owner can switch on audit events and see every attempt." What did we see?

Show the answer

The owner got 403. That was for the change and for a read, from a laptop outside the allowed network and from the lab VPC. We searched two log instances and found no vault events, not even for the refused delete. So before you tell anyone the owner can audit the vault, check that the events appear in your own account.

"A Defender admin who deletes the archive and the target removes the data from the vault." What happened?

Show the answer

The vault kept the data. Three archive copies were marked deleted and the target was removed, but the prefix we checked still held 7 versions, with the same object keys, and the lock hadn't changed. The vault stayed active. That cluster held only the read key, so the test doesn't show what the archive-delete task would do with a write key.

"A vault that holds locked objects cannot be deleted." What did our test show?

Show the answer

The call was accepted and the vault stayed in "deleting". IBM's page says a vault with locked objects can't be deleted. In our lab the call returned 202, and at 16:25 UTC the write key could still list and read all three locked objects. This was a test vault with no data of value.

Step 5 · Check yourself

Three questions

A holder of the write key tries to delete a locked version. What is the result in our lab?

Show the answer

403 "Access Denied because object protected by object lock". The read key, the instance HMAC key and the owner token also got 403.

The write key writes to an object that already holds locked content. What does the vault do?

Show the answer

It adds a new version. The PUT on the probe object gave 200 and a new latest version, and the first version still returned the original content.

Which key could read an object's lock?

Show the answer

The read key. The write key got 403 on the lock read.
