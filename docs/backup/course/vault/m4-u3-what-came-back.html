Unit 3 of Module 4

What was recovered, and two things to check

By the end of this unit you'll be able to say what the rebuild recovered, how it was checked, and two things to check when you plan your own recovery.

About 10 minutesNo account needed5 steps

Northgate Freight, a made-up haulier, has rebuilt its systems from the vault, and its directors will ask whether everything was recovered. In the second test, every file and the database were recovered exactly as they were before the attack. This unit also shows two things to check when you plan your own recovery.

We ran the rebuild twice in our lab. The second test is the one in units 4.1 and 4.2, on a new cluster with only the read key. The first test was an earlier run on a third cluster that also had only the read key, with a much larger set of Linux files. Each is a single run.

Terms used. Hard-linked file: a Linux file whose name points to the same data as another name. Retrieve and restore: retrieve downloads a backup from the vault to the new cluster, and restore writes its data back to a server.

Step 1 · Explore the parts

What the second test recovered

We restored each clean run to a new location and checked it against a record made before the attack. All three restores succeeded, and every file and the database matched.

Workload       Restored to                 Check
Linux files    /v7restore/data             sha256sum -c against the clean manifest: 503 of 503
Windows files  C:\v7restore\data           SHA-256 against the clean list: 503 match, 0 bad, 0 missing
SQL            labdb_v7b, a new database   100000,-108923937 (the clean value)

The restored database labdb_v7b read 100000,-108923937. What does that mean?

Show the answer

It equals the clean value. The attacked labdb still read -426859948 after the restore, so the restored database was recovered from the clean run.

Why did we restore to a new location rather than the original server?

Show the answer

A retrieved group can't restore to the original. In the first test the console refused it with "Restore of a database to the original source is not allowed for remote jobs", so we restored to new locations.

Step 2 · Click through the console

What the console shows before the restore

After the download, each retrieved group lists its snapshots. Click where you'd click. After two misses, the page marks the right place.

In Recoveries, each retrieved object has three snapshots. Which one do you restore?

Show the answer

The clean vault copy. The three are a metadata-only local copy, the clean vault copy and the infected vault copy. Pick the clean vault copy. In the first test, a restore from the metadata-only copy gave "File lookup failed".

How did we check the Linux files?

Show the answer

With sha256sum -c against the manifest, which was made before the attack. 503 of 503 matched. The next step shows why it's worth checking the files as well as the status.

We recorded this as a pass with a known gap, and it's the first thing to check in your own recovery.

Which files came back empty?

Show the answer

The hard-linked files. 13,913 of them came back empty. An earlier test found the same thing and traced the cause to the file backup rather than the vault. So after a restore, check hard-linked Linux files: their content comes from the file backup, not the vault.

Watch for this. These are the first test's times in our lab. Linux: retrieve 17 minutes and restore 38 minutes. Windows: retrieve about 1 minute and restore 1 minute 22 seconds. SQL: restore 1 minute 32 seconds. We didn't record times in the second test.

Step 4 · Spot the fault

The note leaves out the VMs

Northgate's backup admin drafts a note for the directors: "We rebuilt every workload from the vault alone, and every restore said Succeeded." Which workload has she left out, and what else should she check?

Which workload does the note leave out?

Show the answer

The OpenShift VM. Restore OpenShift VMs to the cluster they were backed up from; retrieving them to a new cluster failed in our first test. On its own cluster, the same VM backup restored from the vault in 6 minutes 6 seconds, with 20 of 20 files matching. On the new cluster, indexing succeeded but the snapshot failed with "Cannot find magneto view for icebox view", and the VM registration stayed Pending for 29 minutes. The second test didn't try the VMs.

What found the empty Linux files?

Show the answer

The checksum check. In an earlier test the recovery reported Succeeded, and the checksum check found 13,902 files that differed. So check the files as well as the status.

Watch for this. In the second test, Linux, Windows and SQL were recovered exactly as they were before the attack. The first test showed two things to check in your own recovery: hard-linked Linux files, and OpenShift VMs restored to a different cluster.

Step 5 · Check yourself

Three questions

How many files matched on the Windows server in our lab?

Show the answer

503 of 503. SHA-256 against the clean list: 503 match, 0 bad, 0 missing.

In the first test, how did the Linux check come out?

Show the answer

167,639 matched. The hard-linked files are the ones to check after a restore. In the second test, all 503 files matched.

What happened to the OpenShift VM in the first test?

Show the answer

The retrieve to a new cluster failed at the snapshot. On its own cluster the VM restored from the vault, so restore VMs to the cluster they were backed up from.
