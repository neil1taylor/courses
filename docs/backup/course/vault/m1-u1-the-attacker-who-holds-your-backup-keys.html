Unit 1 of Module 1

The attacker who holds your backup keys

By the end of this unit you'll know what an attacker with stolen backup keys could try against a Cyber Vault, what the vault refused in our tests, and the one change it still allowed.

About 10 minutesNo account needed5 steps

Northgate Freight is a made-up haulier. It already backs up with IBM Storage Defender Data Protect. Its directors want to know what happens if an attacker gets the backup admin's keys.

Every result in this unit comes from a test in our lab.

Terms used. HTTP 403 and HTTP 200: HTTP 403 is the answer a web service gives when it refuses a request, and HTTP 200 is the answer when the request worked. Bypass header: a request option that asks storage to ignore a lock. The vault doesn't honour it. VPC: a virtual private cloud, which is a private network that an account builds inside IBM Cloud. Endpoint: the web address a service answers on. IBM Cloud gives object storage a public, a private and a direct one. Pod: one running piece of software on an OpenShift cluster. Data chunk: one piece of archived data, stored in the vault as its own object.

Step 1 · Explore the parts

Who holds which key

A Cyber Vault comes with two keys. The backup cluster gets the write key. You keep the read key somewhere else and use it only to recover. An attacker might get either key, or both.

Which key does the backup cluster hold when it archives to the vault?

Show the answer

The write key. The steps in the IBM Cloud console tell you to give the write key to the backup cluster and keep the read key apart. A new cluster that recovers from the vault needs only the read key, and you'll see that in Module 4.

In our tests, what could the write key do besides write?

Show the answer

It could list and read. In our test the write key could write an object with a lock, then read it, list it and check it. It couldn't read the lock. The read key could.

Now suppose the attacker also has the Data Protect admin login, and uses it to delete the archive copies and the vault target in Data Protect. What's left in the vault?

Show the answer

The data, still locked. In our test we deleted the archive records and the target in Data Protect. The vault still had the same 7 object versions under the prefix we checked, and the lock on the data chunk we checked hadn't changed. One thing to keep in mind: that cluster held only the read key, which can't delete anything, so the test doesn't show what the same delete would do from a cluster with the write key.

Step 3 · Spot the fault

What the IT manager wants to tell the directors

Northgate's IT manager wants to tell the directors: "Someone with the write key can't change anything in the vault." Is that true?

What did our test show?

Show the answer

No, it isn't true. On a test object, a write with different content returned 200 and made a new version. The list showed two versions, and the first one still returned the original content, but the latest version was now the new content. So someone with the write key can hide the real data behind a new version. The old version stays.

Now the attacker is on a server in a different network, and has a valid write key. What did the vault do in our test?

Show the answer

It refused. A pod in a second VPC, with a valid write key, got 403 on the direct and the public endpoint, and no answer at all on the private one. The same request from the allowed network got 200. We also tried from a laptop on the VPN with a valid write key, and the public endpoint gave 403 there too.

Watch for this. A locked object can't be deleted and its lock can't be shortened, but that doesn't stop someone writing a new version on top. We tested this on a test object, not on a Data Protect archive.

Show the answer

The second one. It says what the tests in this unit showed. The first goes too far, because step 3 showed that a write key can still add a version. The third is wrong, because the vault is logically isolated and isn't a physical air gap. Unit 1.3 covers that.
