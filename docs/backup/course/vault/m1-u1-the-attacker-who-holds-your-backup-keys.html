Unit 1 of Module 1

The attacker who holds your backup keys

By the end you can say what an attacker with stolen backup keys could try against a Cyber Vault, what the vault refused in our tests, and the one thing it does not stop.

About 10 minutesNo account needed5 steps

Northgate Freight is a made-up haulier. It already backs up with IBM Storage Defender Data Protect. Its board asks one question: what happens if an attacker gets the backup admin's keys?

Every result in this unit comes from tests in our lab on 5 and 6 October 2026. The vault is IBM Cloud Cyber Vault (Beta), in us-south, with no SLA.

Step 1 · Explore the parts

Who holds which key

A Cyber Vault comes with two keys. The backup cluster gets the write key. The read key is kept apart and is used to recover. An attacker might get either, or both.

Which key does the backup cluster hold when it archives to the vault?

Show the answer

The write key. The console steps say to give the write key to the backup cluster and keep the read key apart (in the console). A new cluster that recovers from the vault needs only the read key; Module 4 shows that.

In our tests, what could the write key do besides write?

Show the answer

The write key could write an object with a lock, read it, list and check it. It could not read the lock; the read key could (5 October 2026).

The attacker also has the Data Protect admin login and deletes the archive copies and the vault target in Data Protect. What does the vault keep?

Show the answer

In our test on 6 October 2026 the archive records and the target were removed in Data Protect. The vault kept the same 7 object versions under the prefix we checked, and the lock on the data chunk we checked was unchanged. That cluster held only the read key, which cannot delete. The test did not show what the same delete would do with a write key.

Step 3 · Spot the fault

A sentence for the board

Northgate's first draft for the board says: "An attacker with the write key can change nothing in the vault." Something in it is too strong.

What did our test find?

Show the answer

On a probe object, a write with other content returned 200 and made a new version. The list showed two versions, and the first still returned the original content. But the latest version was now the new content. A holder of the write key can hide the latest data; the old version stays (5 October 2026).

The attacker sits on a server in a different network and has a valid write key. What did the vault do in our test?

Show the answer

On 6 October 2026 a pod in a second VPC, with a valid write key, got 403 on the direct and the public name and no answer on the private name. A control from the allowed network got 200. From a laptop on the VPN, with a valid write key, the public endpoint also gave 403.

Watch for this. A locked object cannot be deleted or shortened. That does not stop a new version being written on top. The tested case is a probe object, not a Data Protect archive.
