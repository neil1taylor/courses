Unit 2 of Module 1

Certificates for the VPN

By the end of this unit you'll be able to name the certificates a VPN server needs and who issues each, say which secret the server trusts for client certificates, and find why a VPN server refuses a certificate.

About 10 minutesNo account needed5 steps

Northgate Freight is a made-up haulier. Its security team wants each VPN user, each person who connects, to prove who they are with their own certificate before the VPN lets them in.

Every command and line of output in this unit comes from real runs, and the limits come from IBM's pages.

Step 1 · Explore the parts

Who issues what

IBM Cloud Secrets Manager is an IBM Cloud service that stores secrets such as certificates, and a VPN server for VPC takes its certificates from it. A certificate authority, or CA, is the party that signs certificates so that others can check who a certificate belongs to. The VPN server needs a server certificate, and a client certificate for each VPN user, signed by a CA the server trusts. Select a part to see what it is and what goes wrong without it.

↑ tap any box

Root CA

The top certificate authority, made as a configuration in Secrets Manager. In this chain it signs only the intermediate CA. Its keys stay in the service, and the service can renew certificates.

Watch for this. Switch on issuing_certificates_urls_encoded and crl_distribution_points_encoded. A certificate cannot live longer than its CA.

Intermediate CA

A CA that the root signs. Certificates are issued from this one, so the root never signs a server or client certificate itself.

Watch for this. Switch on the same two settings here too. Without them the VPN server refuses the certificate with vpn_server_parent_ca_url_missing.

Template

The rules for certificates issued from the intermediate CA: the allowed domain, whether a certificate may be a server or a client certificate, and its lifetime. This one allows vpct.internal and subdomains, as both server and client.

Watch for this. A template cannot be attached to the root CA directly. The error is certificate authority ... couldn't be found for this template.

Server certificate

The certificate the VPN server shows to clients. Here its common name is vpn-server.vpct.internal, issued as a secret.

Watch for this. IBM says a server certificate needs the certificate, the private key and the intermediate certificate.

Client certificate

The certificate a VPN user presents to prove who they are. Here its common name is client1.vpct.internal. The client keeps its own certificate, its key and the intermediate CA certificate.

Watch for this. IBM says a client certificate used for authentication needs the certificate and the intermediate certificate.

Client CA secret

The CA the server trusts for client certificates. Use the secret of a client certificate that you won't revoke. The server then reads the revocation list that the CA publishes, and refuses a revoked certificate.

Watch for this. With an imported CA secret as the client CA, the server never used the revocation list that Secrets Manager publishes, and gave no error.

Authorization

An IAM authorization that lets the VPN service read secrets, with the role SecretsReader, scoped to the Secrets Manager instance.

Watch for this. Look at the existing authorizations first, because other teams share the account. The lab account already held two broader ones, so a scoped one proved nothing there, and it is still the safe one to keep.

ibmcloud secrets-manager configuration-create --configuration-prototype='{"config_type":"private_cert_configuration_root_ca","name":"vpct-root-ca","common_name":"vpct-ca","max_ttl":"720h","crl_disable":false,"crl_distribution_points_encoded":true,"issuing_certificates_urls_encoded":true}'
ibmcloud secrets-manager configuration-create --configuration-prototype='{"config_type":"private_cert_configuration_intermediate_ca","name":"vpct-intermediate-ca","common_name":"vpct-intermediate-ca","max_ttl":"700h","signing_method":"internal","issuer":"vpct-root-ca","crl_disable":false,"crl_distribution_points_encoded":true,"issuing_certificates_urls_encoded":true}'
ibmcloud secrets-manager configuration-action-create --name vpct-root-ca --config-type private_cert_configuration_root_ca --config-action-prototype '{"action_type":"private_cert_configuration_action_sign_intermediate","intermediate_certificate_authority":"vpct-intermediate-ca","common_name":"vpct-intermediate-ca","ttl":"650h"}'
ibmcloud secrets-manager configuration-create --configuration-prototype='{"config_type":"private_cert_configuration_template","name":"vpct-vpn-template","certificate_authority":"vpct-intermediate-ca","allowed_domains":["vpct.internal"],"allow_subdomains":true,"server_flag":true,"client_flag":true,"max_ttl":"600h","ttl":"600h"}'
ibmcloud secrets-manager secret-create --secret-prototype='{"name":"vpct-vpn-server-cert-sm","secret_type":"private_cert","certificate_template":"vpct-vpn-template","common_name":"vpn-server.vpct.internal","ttl":"500h","rotation":{"auto_rotate":false}}'
ibmcloud secrets-manager secret-create --secret-prototype='{"name":"vpct-vpn-client1-cert","secret_type":"private_cert","certificate_template":"vpct-vpn-template","common_name":"client1.vpct.internal","ttl":"500h","rotation":{"auto_rotate":false}}'

Step 2 · Choose it

Who issues the certificates

Chapter 72 gives two recipes. Pick one for each case, then read the worked answer.

Northgate has no CA yet. It wants the keys kept in a service that can renew the certificates. What should it use?

Show the worked answer

Secrets Manager as the CA. The keys stay in the service and it can renew the certificates. The chapter recommends it.

Northgate already runs Easy-RSA. What should it use, and what changes for revocation?

Show the worked answer

Easy-RSA is IBM's own recipe and the right one if you already run it. With your own CA the VPN server does not read a revocation list from the CA, so revoking a certificate needs a list uploaded to the server. The next module shows how.

With the Secrets Manager recipe, which secret does --client-ca take?

Show the worked answer

A client certificate secret that you won't revoke. --client-ca takes a secret of its own, the client CA. It is not the server certificate.

Step 4 · Spot the fault

The VPN server refuses a certificate

Chapter 72 gives two causes for a VPN server that rejects a certificate. Match each cause to its fix.

The CAs were made without the settings that encode their issuing URLs. The VPN server answers vpn_server_parent_ca_url_missing. What fixes it?

Show the answer

Both settings on, on both CAs. Those are issuing_certificates_urls_encoded and crl_distribution_points_encoded, on the root CA and the intermediate CA.

A client CA secret imported from the root certificate alone is refused with Can not get the mandatory property 'intermediate'. What fixes it?

Show the answer

Import the CA certificate, and import it again as its intermediate. A client CA secret needs an intermediate. The same step applies when you use your own CA.

Step 5 · Check yourself

Three questions

Which two settings must be on for both CAs, or the VPN server refuses the certificate?

Show the answer

Issuing URLs encoded, and CRL distribution points encoded. Without them the server answers vpn_server_parent_ca_url_missing.

You try to attach a template to the root CA. What happens, and where does the template go?

Show the answer

It fails with certificate authority ... couldn't be found for this template. Attach the template to the intermediate CA. A certificate also cannot live longer than its CA.

You update an imported certificate secret in Secrets Manager. Does the VPN server see the new certificate?

Show the answer

No. IBM says the VPN server does not see an imported certificate that you update. Import it again, which gives a different CRN, and update the server to use it.

A CA in Secrets Manager signs an intermediate CA, and a template on the intermediate issues the server and client certificates. Both CAs need their issuing URLs and revocation list addresses switched on. The client CA is a client certificate secret you won't revoke.
