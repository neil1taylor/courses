Unit 1 of Module 2

Revoke a certificate on a VPN server

By the end of this unit you'll be able to revoke a client certificate and predict when a VPN server refuses it, say what happens to a session that is already open, and give a server that uses its own CA a revocation list that works.

About 10 minutesNo account needed6 steps

Northgate Freight is a made-up haulier. One of its administrators loses a laptop, and its security team needs the laptop's certificate to stop working.

Every command and line of output in this unit comes from real runs, and the first statements come from IBM's pages.

Step 1 · Explore the parts

From a revoked certificate to a refused one

A revoked certificate is one its CA withdrew before it expired. Select a part to see what it does, and what the runs showed.

↑ tap any box

Revoke the secret

A secret action revokes the client certificate. The CA rebuilt and published its list within 6 seconds. You do not rotate anything.

Watch for this. The CA must have been made with both CRL building and CRL distribution points on. IBM says a revoked certificate is then "no longer trusted by the applications after one hour".

VPN server

Create the server with a Secrets Manager private certificate secret as the client CA, and upload no list. In two runs the revoked certificate was refused within 100 seconds, and the good certificate connected throughout. IBM's page says an hour.

Watch for this. The server never says no. It stops answering, and the client gives up after 60 seconds with TLS key negotiation failed. An imported CA secret as the client CA never used the list.

Open session

A session that was open when the certificate was revoked stayed up. One was still passing traffic almost 30 minutes later, with no packet loss.

Watch for this. No way to end such a session was run. Deleting the VPN client and changing the server were not tried.

Your own CA

A CA made with openssl has no distribution point that Secrets Manager serves, so the server never reads a list from it. You revoke the certificate in that CA, write the list and upload it to the server.

Watch for this. Give --client-ca as well. Without it the command returns success and stores nothing. The CLI has no option that removes a list, so use the REST API for that.

Next-update date

Each list carries a date after which the list itself is out of date. Here the CA writes it 7 days after the list is written.

Watch for this. After that date the VPN server refuses every client, the good certificate too. Write a new list before then and upload it again.

Client CA secret

When this secret expired, was rotated, or was revoked, a good client certificate connected and a revoked one was refused, and the server stayed stable with health state ok.

Watch for this. After an expiry or a revocation, point the server at another certificate secret. A rotation needs nothing.

ibmcloud secrets-manager secret-action-create --id <vpct-vpn-revoked-cert-id> --secret-action-type private_cert_action_revoke_certificate
ibmcloud is vpn-server-create --name vpct-prod-vpnserver-rev --vpc vpct-prod --subnet vpct-prod-vpn-z1 --client-ip-pool 172.16.4.0/22 --cert <server-cert-crn> --client-auth-methods certificate --client-ca <crn-of-the-vpct-vpn-good-cert-secret> --sg vpct-prod-vpnserver-sg --enable-split-tunnel true --resource-group-name vpct-lab
openssl ca -config ca.cnf -revoke revoked.crt
openssl ca -config ca.cnf -gencrl -out crl.pem
ibmcloud is vpn-server-update <server> --vpc vpct-prod --client-auth-methods certificate --client-ca <client-ca-crn> --client-crl @crl.pem

Step 3 · Run it

Revoke, then try to connect

Run each command in turn. The output is what the lab returned, trimmed to the lines that matter.

bash
ibmcloud secrets-manager secret-action-create --id <vpct-vpn-revoked-cert-id> --secret-action-type private_cert_action_revoke_certificate
Action Type               private_cert_action_revoke_certificate
Revocation Time Seconds   1794584968

The CA rebuilt and published its list within 6 seconds.

The probe now connects with the revoked certificate every few seconds. What does the client see?

Show the answer

No answer, then a timeout. The server never says no. It stops answering, and the client gives up after 60 seconds.

sudo openvpn --config revoked.ovpn --verb 4
[15:49:26Z] revoked-cert: CONNECTED
[15:50:45Z] revoked-cert: TIMEOUT
TLS Error: TLS key negotiation failed to occur within 60 seconds (check your network connectivity)
TLS Error: TLS handshake failed

The refused attempt began 38 seconds after the revocation. The first error line also appeared when the list was out of date, so it alone does not say which cause it is.

# your own CA: revoke, write the list, and check it

openssl ca -config ca.cnf -revoke revoked.crt
openssl ca -config ca.cnf -gencrl -out crl.pem
openssl crl -in crl.pem -noout -issuer -lastupdate -nextupdate -crlnumber
Revoking Certificate 1001.
Database updated
issuer=CN = vpct-own-ca
lastUpdate=Nov 13 18:28:40 2026 GMT
nextUpdate=Nov 20 18:28:40 2026 GMT
crlNumber=0x1000

The next-update date is 7 days after the list was written.

# the same upload without --client-ca

ibmcloud is vpn-server-update <server> --vpc vpct-prod --client-auth-methods certificate --client-crl @crl.pem
Status                       stable
{"lifecycle_state":"stable","auth":{"method":"certificate","has_crl":false,"has_ca":true}}

Status stable and exit code 0, but has_crl is false: nothing was stored.

Step 4 · Predict and spot the fault

Open sessions, and an upload that did nothing

A session was open when its certificate was revoked. What happens to it?

Show the answer

It stays up and keeps passing traffic. One session was still passing traffic almost 30 minutes after its certificate was revoked. On a server that used an uploaded list, a session ended only when its TLS keys ran out, 75 minutes after the list was applied. No way to end such a session was run.

You uploaded a list without --client-ca and saw Status stable with exit code 0. Does the server refuse the revoked certificate?

Show the answer

No. The REST API shows has_crl false, and the revoked certificate still connects. Give --client-ca with --client-crl. With it, the revoked certificate was refused at an attempt 36 seconds after the command.

Step 5 · Spot the mistake

Which set-up mistake is it?

Each set-up below let a revoked certificate in, and none gave an error. Match the symptom to the mistake.

On a VPN server, the revoked certificate connected after 75 minutes and after 120 minutes, on a new server and after a list rotation. No error.

Show the answer

An imported CA secret as the client CA. The VPN client CA must be a Secrets Manager private certificate secret.

The VPN server took the CA without an error, and the revoked certificate connected 37 minutes after it was revoked.

Show the answer

A CA without CRL distribution points. It writes no list address into its certificates, so nothing can refuse them.

The VPN server accepted a list from the root, but the intermediate signed the client. The revoked certificate still connected.

Show the answer

A list from the wrong CA in the chain. The certificate was refused 58 seconds after the intermediate's list was applied.

Step 6 · Check yourself

Three questions

Which client CA lets a VPN server read the list that Secrets Manager publishes?

Show the answer

A Secrets Manager private certificate secret. With an imported CA secret as the client CA, the server never used the list, and gave no error.

IBM says a revoked certificate is untrusted after one hour. How long did the VPN server take in the runs?

Show the answer

Under two minutes. In two runs the revoked certificate was refused within 100 seconds of the revocation.

The client CA secret expires. What happens to a revoked certificate, and what do you do?

Show the answer

It is still refused, before and after the expiry date. Point the server at another certificate secret. The server was stable with health state ok 17 to 19 seconds after the update.
