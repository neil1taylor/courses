Unit 4 of Module 5

Watch and troubleshoot a VM

By the end you can say which layer to look at when a VM misbehaves, recognise healthy output, and read broken output without being fooled by it.

About 10 minutesNo cluster needed5 steps

Northgate Freight is a made-up company. Its admins read vCenter alarms. A ROVS VM has layers, and a fault shows in one of them while its cause may sit in another.

Every command, output and fact in this unit comes from real runs on lab clusters, recorded in tutorial chapters 42, 45 and 50. The review question repeats one from unit 4.2.

Step 1 · Explore the parts

Where to look, layer by layer

Chapter 45 groups its read-only diagnostic commands by layer. Select a layer in the drawing to see what to look for and which commands belong to it. You can also click a line.

↑ tap any box

VM layer

Start at the top. A VM set to run that has no VMI is being prevented from starting. The events are not here: on the cluster used, oc describe vm showed only SuccessfulCreate. They sit on the pod.

From vSphere: a VM that will not reach Running is like a power-on that fails. A rough mapping, not an IBM statement.

Pod layer

Pending: read the pod events for scheduling failures. CrashLoopBackOff: QEMU is crashing, so read the compute container's log.

Watch for this. These logs are the hypervisor's view. Your guest's own logs appear in none of them. Getting guest logs off a VM needs an agent inside the VM.

Network layer

For a localnet network, the policy must be applied and its enactment must succeed on each node. The two pre-configured policies are IBM's: the add-on reconciles them and will revert your edit. Three values must agree across the chain: the VLAN ID on the attachment and on the CUDN, and the bridge-mapping name and the CUDN's physicalNetworkName.

Storage layer

A PVC should be Bound and a DataVolume Succeeded. On ODF the Ceph health command needs nothing installed. A degraded Ceph cluster affects VM disk I/O directly, and a badly degraded one blocks it and hangs the VMs.

From vSphere: this is datastore health.

Operator layer

virt-handler runs on every node. When a VM fails to start or migrate, its log often holds the root cause. virt-controller makes the cluster-level decisions, so read its log when VMs are stuck in Scheduling. The add-on owns these operators: collect their output, do not patch them.

VPC layer

ibmcloud is bare-metal-server-network-attachments does not work here. It addresses a bare metal server in your account, and ROVS workers are provisioned in IBM's account. Use ibmcloud ks vni ls.

# VM layer
oc get vm                              # All VMs
oc get vmi                             # Running VM instances
oc describe vm my-vm                   # VM details and events

# Pod layer
oc get pods -l vm.kubevirt.io/name=my-vm  # virt-launcher pod
oc describe pod virt-launcher-...      # Pod details and events
oc logs virt-launcher-... -c compute   # QEMU/hypervisor logs

# Network layer
oc get clusteruserdefinednetwork        # Cluster-scoped network definitions
oc get net-attach-def -n my-namespace             # Namespace network attachments
oc get nncp                            # Node network policies
oc get nnce                            # Per-node network enactments

# Storage layer
oc get pvc                             # Persistent volume claims
oc get dv                              # DataVolumes
oc get cephcluster -n openshift-storage  # ODF health

# Operator layer
oc get pods -n openshift-cnv           # OpenShift Virtualization pods
oc logs -n openshift-cnv virt-handler-...   # Node-level VM manager
oc logs -n openshift-cnv virt-controller-... # Cluster-level VM scheduler

# VPC layer (ROVS: ks, not is)
ibmcloud ks vni ls --cluster-id <cluster-id>   # VNI attachments and their VLANs
ibmcloud ks workers --cluster <cluster>        # Worker IDs, zones and state
Step 2 · Predict, then run it

What healthy looks like

A command that only speaks when something is broken is easy to misread. Learn the healthy output first. The console also has dashboards under Virtualization, Overview and a Metrics tab on each VM, and PromQL runs under Observe, Metrics. The QEMU guest agent is the counterpart of VMware Tools, and these dashboards are the vCenter Monitor tab. Rough mappings, not IBM statements.

bash

# the network policies the add-on pre-configures

oc get nncp
NAME        STATUS      REASON
br-eth1     Available   SuccessfullyConfigured
vpc-vlans   Available   SuccessfullyConfigured

Available and SuccessfullyConfigured is the all-clear.

There is one enactment per policy per node. This cluster has three workers and two policies. How many rows do you expect when all is well?

Show the answer

Six. A missing row is as much a fault as a failing one.

# the per-node result of each policy

oc get nnce
NAME                                STATUS      REASON
kube-...-rovspoo-00000167.br-eth1   Available   SuccessfullyConfigured
kube-...-rovspoo-00000167.vpc-vlans Available   SuccessfullyConfigured
kube-...-rovspoo-000002a1.br-eth1   Available   SuccessfullyConfigured
kube-...-rovspoo-000002a1.vpc-vlans Available   SuccessfullyConfigured
kube-...-rovspoo-0000039f.br-eth1   Available   SuccessfullyConfigured
kube-...-rovspoo-0000039f.vpc-vlans Available   SuccessfullyConfigured

Six rows, all Available. The chapter shows only the healthy case: making a FailedToConfigure would have meant breaking an IBM-managed policy on a shared cluster.

# ODF health, with nothing installed

oc get cephcluster -n openshift-storage
NAME                             DATADIRHOSTPATH   MONCOUNT   AGE   PHASE   MESSAGE                        HEALTH
ocs-storagecluster-cephcluster   /var/lib/rook     3          37d   Ready   Cluster created successfully   HEALTH_OK

PHASE Ready and HEALTH_OK together are the all-clear.

HEALTH_WARN with Ready is usually capacity or a single OSD. HEALTH_ERR, or a phase that is not Ready, is not something these checks can fix.

Step 3 · Spot the fault

Two VMs that will not run

Two failures were made on purpose on a lab cluster, in a scratch namespace. Both VMs show READY False.

$ oc get vm
NAME       STATUS               READY
badimage   ImagePullBackOff     False
toobig     ErrorUnschedulable   False

Where do you read the events that name the cause?

Show the answer

On the cluster used, oc describe vm showed only SuccessfulCreate. The VM's Status column and the PodScheduled condition named the same two causes in shorter form.

What do the two statuses tell you?

Show the answer

oc describe pod on the toobig launcher pod gave FailedScheduling with 0/3 nodes are available: 3 Insufficient memory: free up resources or add nodes. On badimage it gave ErrImagePull, then ImagePullBackOff: check the image URL and the pull secrets.

A PVC event reads ProvisioningFailed with storageclass.storage.k8s.io "..." not found. What do you check?

Show the answer

The named storage class does not exist. Chapter 45 lists this beside FailedScheduling, ErrImagePull and ErrImportFailed as the common start events.

Step 4 · Spot the fault

Outputs that look wrong

Two outputs that read like faults, and one fault that shows no error at all.

$ oc get pods -l kubevirt.io/vm=scratch-w2c-vm-virt
No resources found in scratch-w2c-mig namespace.

$ oc get secret ibm-kp-secret ceph-csi-kms-token -n openshift-storage
Error from server (NotFound): secrets "ibm-kp-secret" not found
Error from server (NotFound): secrets "ceph-csi-kms-token" not found

The first command found no pod, and the VM is running. What is wrong?

Show the answer

With vm.kubevirt.io/name the same VM's pod appeared: virt-launcher-scratch-w2c-vm-virt-mgmhn, 2/2 Running. You would otherwise troubleshoot a pod that is not missing. A disk from a dataVolumeTemplate carries no VM-name label at all, so read the claim names out of the VM object.

Both KMS secrets are NotFound. Is that a fault?

Show the answer

This is the output from a healthy ROVS cluster that does not use KMS. Check it only when a PVC is stuck in ExternalProvisioning and an encrypted class is in play.

Every node is Ready. Every VM object reports Running. The VMs have gone quiet. What do you check first?

Show the answerVMs hang. They do not fail over.

With 2 of 3 copies, I/O continues. With 1 of 3, Ceph blocks all I/O to the affected placement groups, and nothing on the VM side reports an error. So "the VMs stopped" cannot be your signal: alert on placement group health, and give CephOSDNearFull a named owner. That table describes expected Ceph behaviour; no pool was made to lose copies.

Step 5 · Check yourself

Four questions

oc get vmi my-vm -o jsonpath='{.status.guestOSInfo}' returns nothing. What does that mean?

Show the answer

With the agent, OpenShift reports the hostname and OS, interface addresses, filesystem usage and the guest's own memory use. Without it, the VM is seen only from outside.

What does oc logs virt-launcher-my-vm-xxxxx -c compute show?

Show the answer

None of the KubeVirt logs are your guest's logs. Guest and application logs need an agent inside the VM.

You apply a PrometheusRule in a user namespace. It is accepted without error, and the alert never fires. Why?

Show the answer

The API server accepts the rule and nothing evaluates it, with no error. Red Hat's prerequisite is that monitoring for user-defined projects is enabled. The OVE licence entitles User Workload Monitoring for VMs only.

Review from unit 4.2. After you grow a PVC, df -h / in the guest still shows the old size. Is the resize broken?

Show the answer

The block device grew live; the partition and filesystem did not. Use growpart, then xfs_growfs or resize2fs.
