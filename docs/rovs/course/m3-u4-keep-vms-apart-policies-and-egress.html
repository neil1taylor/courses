Unit 4 of Module 3

Keep VMs apart: policies and egress

By the end you can say which control stops which traffic, and name the gaps that a vSphere admin, used to NSX, would not expect.

About 10 minutesNo cluster needed5 steps

Northgate Freight is moving off vSphere. The company is made up; the output in this unit is real. Its security team wants the same separation it had with NSX. It will not all come from one place.

Every statement and output in this unit comes from tutorial chapters 15, 26 and 27, apart from the review question, which comes from chapter 12. The VMware comparisons are rough mappings, not IBM statements.

Step 1 · Predict

A security group with no inbound rule

Three VMs on one localnet network. The server's VPC security group has no inbound rule. One client runs on the server's worker, one on another worker. Both clients' groups allow all traffic.

Each client sends a ping and an HTTP request to the server. Which clients get through?

Show the answerA hole, not a footnote.

client1's ping and HTTP succeeded and client2's were blocked. Traffic between VMs on the same worker is switched inside OVS and never reaches the VPC fabric, where security group rules apply. The server's log showed client1's VPC address, so the traffic took no other path.

Later, a live migration or node drain puts client2 on the server's worker. What do you expect?

Show the answer

The same pair of VMs is filtered on different workers and unfiltered on the same one. A rule set that works in testing can silently stop applying after a migration or a drain. A security group is not a tenant boundary on its own.

Step 2 · Run it

A policy that is in force, and a VM it does not touch

Two VMs on a secondary Layer 2 network, in two projects on two workers. Run each command in turn. The output is what the cluster returned in chapter 26.

bash

# from the client VM, before any policy

ping -c 3 192.168.100.11
3 packets transmitted, 3 received, 0% packet loss

The path works.

curl -s -m 6 -o /dev/null -w "HTTP=%{http_code}\n" http://192.168.100.11:5432/
HTTP=200

Both ping and HTTP work with no policy.

# a deny-all ingress policy goes on the destination's project

oc describe networkpolicy deny-all-ingress -n scratch-w2b-l2b
Spec:
  PodSelector:     <none> (Allowing the specific traffic to all pods in this namespace)
  Allowing ingress traffic:
    <none> (Selected pods are isolated for ingress connectivity)
  Not affecting egress traffic
  Policy Types: Ingress

The chapter shows only this part of the output.

It was in force: an ordinary pod on the primary network went from HTTP=403 to a dropped request, curl exit code 28.

The policy is in force and selects every pod in the project, including the VM's launcher pod. Will the VM's Layer 2 address still answer?

Show the answer

Run the same two commands again.

# same VMs, same commands, nothing else changed

ping -c 2 192.168.100.11
2 packets transmitted, 2 received, 0% packet loss
curl -s -m 6 -o /dev/null -w "HTTP=%{http_code}\n" http://192.168.100.11:5432/
HTTP=200

Untouched. One interface was enforced and one was not.

A NetworkPolicy covers a pod's primary network, not a secondary one.

Step 3 · Design it

Which policy covers which network?

Chapter 26 measured this on a ROVS cluster as delivered. Security groups plus network policies are not a drop-in replacement for the NSX distributed firewall.

Northgate's three-tier app needs its tier boundary enforced by the platform, inside the cluster. Where must the VMs' traffic be?

Show the worked answer

Make the network primary. A primary Layer 2 or Layer 3 network is the pod's primary network, so ordinary NetworkPolicy governs it. It is the only mechanism that the platform enforces and that is available today. The other ways out cost something: a router pod is a single point of failure with a bandwidth ceiling, and a guest firewall is defence in depth that the application owner can switch off. MultiNetworkPolicy worked once turned on, but IBM says it is not officially supported on ROVS.

Do not report a Layer 2 secondary segment as segmented. It is not.

Step 4 · Spot the fault

The namespace that lost the API

An egress firewall is an ordered list: the first rule that matches wins. Northgate ends its list with a catch-all Deny of 0.0.0.0/0 and allows the worker subnet, 10.243.128.0/24. Afterwards everything in the project loses access to the cluster API.

bash

Is the API server's address inside the worker subnet 10.243.128.0/24?

Show the answer

Run the command to see the address.

oc get ep kubernetes -n default
Warning: v1 Endpoints is deprecated in v1.33+; use discovery.k8s.io/v1 EndpointSlice
NAME         ENDPOINTS         AGE
kubernetes   172.20.0.1:2040   37d

Not in the worker subnet, the pod network or the service network.

The warning is expected and harmless.

oc get node <node> -o jsonpath='{.metadata.annotations.k8s\.ovn\.org/host-cidrs}'
["10.243.128.53/24","172.20.0.1/32"]

The API address is in each node's host list.

A rule that allows the nodes covers it, and keeps covering it if it changes.

What is the fix?

Show the answer

Delete the firewall, add the nodeSelector: {} Allow at the top, and apply it again. Or allow the exact address as a /32. An Allow written against the worker subnet does not cover the API address, so it cannot fix this.

Step 5 · Check yourself

Three questions

Review question from Unit 3.1. The VM subnet has a public gateway. Can a host on the internet start a connection to a VM on it?

Show the answer

A public gateway rewrites the source address of outbound traffic. Unsolicited inbound traffic is blocked. Inbound access needs a floating IP or a load balancer.

A project has an egress firewall with a catch-all Deny. Its VM has only a secondary Layer 2 interface. Does a ping to a VM outside the allow list fail?

Show the answer

In the run, the ping and an HTTP request both succeeded. An egress firewall is programmed on the project's primary network and nowhere else. No cluster resource available as delivered on ROVS filters a secondary interface.

An on-premises firewall rule needs one stable source address for Northgate's localnet VMs. What gives you that?

Show the answer

A localnet VM already has a stable, known address that does not change when it live-migrates. Reserve it and pin it, or write the external rule against the subnet range. No topology in these chapters gets a working EgressIP.
