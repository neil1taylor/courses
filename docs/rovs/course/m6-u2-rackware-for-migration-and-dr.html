RackWare for migration and DR

By the end you can say what RackWare RMM reaches that MTV cannot, which target patterns worked on ROVS, and why a standby machine has to keep running.

About 10 minutesNo cluster needed5 steps

Northgate Freight is a made-up company. It has a few physical servers that MTV cannot see, and some VMs that need a second copy somewhere else.

No public source documents RMM as a ROVS migration target. The runs here were on test clusters with RMM 7.7.4.19, and their results should not be carried to another build. Every result in this unit is quoted with that condition. The review question repeats one from unit 6.1.

Step 1 · Explore the parts

How RMM copies a running machine

RackWare RMM does not move disks. It copies the filesystem of a running machine, then rebuilds it on a target. This is the chapter's own sequence. Select a part of the drawing to see what it does and which lines describe it. You can also click a line.

↑ tap any box

The source

RMM logs into the running source over SSH, port 22, or through RWSSHDService on Windows. It inventories the filesystems and snapshots them, with LVM on Linux and VSS on Windows. It never touches the hypervisor, so it does not care whether there is one.

Watch for this. For disaster recovery, protected Linux machines must keep their data on LVM, with 15% of used space free as extents in every volume group. Windows machines need the same 15% as VSS shadow storage.

From vSphere: MTV is roughly cross-vCenter vMotion. RMM is roughly a P2V converter, or Zerto for the disaster recovery case. These are approximate mappings, not IBM statements.

The target

RMM boots the target into a RackWare microkernel, then reformats and re-lays-out its disk to match the source. On RMM 7.7.4.19 this worked on a KubeVirt VM: on a machine built in advance, RMM booted RackWare's neoramfs from the machine's own /boot. It was observed on that version only.

The transfer

The target pulls file data from the source over a reverse SSH tunnel. Two engines do it. RWSync is the default: agentless, slower, tolerant of network outages. TNG is much faster but needs a delta file tracker agent on every source, does not support remote NFS or CIFS mounts, and is more sensitive to outages.

Watch for this. "Agentless" is true of the default engine only. An aggressive recovery point target pushes you to TNG, and then you maintain an agent on every protected source.

After the copy

RMM injects drivers, rewrites the bootloader for the new platform and reboots into the replicated system. Every later pass is a delta sync that repeats the microkernel boot.

Watch for this. RMM logs into the target as root and copies its own private key onto it, so the target can pull from the source. For a migration that exists for a few weeks. For disaster recovery it exists permanently.

1. Discovers the running source over SSH and inventories its filesystems.
2. Snapshots them, using LVM on Linux and VSS on Windows, so the copy is consistent while the system keeps running.
3. Boots the target into a RackWare microkernel, via GRUB on Linux or Windows Boot Manager.
4. Reformats and re-lays-out the target's disk to match the source's partitioning and filesystems.
5. Transfers file data, pulling from the source over a reverse SSH tunnel.
6. Injects drivers, rewrites the bootloader for the new platform, and reboots into the replicated OS.
7. Delta-syncs on every subsequent pass, repeating the microkernel boot each time.
Step 2 · Design it

MTV or RackWare?

Three Northgate sources. Pick a tool for each, then read why.

A Northgate VM runs on vSphere. Which tool?

Show the answer

If the source is vSphere, use MTV. It is documented on ROVS, it was run end to end on the series' own cluster, and it is free. RMM costs $110 per source VM, licence included, at the IBM catalog price.

A Northgate application runs on a physical server. Which tool?

Show the answer

MTV talks to vCenter and has no P2V path. RMM is for physical servers, Hyper-V, Nutanix, KVM, Xen and machines in other clouds. Physical servers are its original use case.

A source VM may only be copied while it is switched off. Which tool allows that?

Show the answer

RMM needs the source powered on, because it replicates a running system over SSH. MTV does not, because it reads the disks through vCenter. RMM also needs inbound SSH to every source, and no hypervisor credentials.

Step 3 · Spot the fault

Two failures with no clear message

Both come from test runs with RMM 7.7.4.19. Read the output, then pick the cause.

A Northgate team stops its Warm target to save cost. At failover, RackWare answers:

No syncs were started

It never contacted the machine, and the failover group stayed stuck.

What is the cause?

Show the answerWarm costs what Hot costs.

RackWare has no power driver for OpenShift or KubeVirt. rw host poweron on a stopped machine fails with Host 'rackware-warm' is powered off and there is no power controller to power cycle it. Starting the machine and repeating the identical command succeeded. The tested Linux machine took about a minute to start. A stopped VPC virtual server behaved the same.

Pilot Light onto the DR cluster, with the RMM on the source cluster. RackWare built the machine on the DR cluster, asked to use the network cudn-rackware-dr2. The machine's definition says:

interfaces: [{"name":"cudn-rackware-dr2","masquerade":{}, ...}]
networks:   [{"name":"cudn-rackware-dr2","pod":{}}]

The RMM polled the machine for 25 minutes, then reported Failed to find reachable IP addresses for new VM. and deleted it.

What is the cause?

Show the answerThe name was kept. The network was not.

The interface keeps the name it was given, but the network behind it is pod. This was seen twice, on RMM 7.7.4.19. No message names the network. Until that changes, Pilot Light onto a ROVS cluster needs an RMM inside each DR cluster. RackWare has not confirmed this as a defect.

Step 4 · Predict

Where the targets worked

The chapter ran failover and failback from an RMM on the source cluster. A solid line worked. The dashed marked line failed.

A 35 GB RHEL 9 machine fails over to the second ROVS cluster, onto an empty target built in advance. About how long on a same-region link?

Show the answer

6 minutes 5 seconds, with RMM 7.7.4.19. Windows Server 2022 took 487 seconds. Failback of the Linux machine took 2 minutes 53 seconds. Because both clusters were in one region, these times are for a same-region link and may be longer over a longer one.

Linux failback stops silently at the status Prt Fallen Back. What do you do before it?

Show the answer

RackWare builds the target's volume group with zero free extents, then refuses to fail back from it. The only record is SYNC_ERROR_INSUFFICIENT_ORIGIN_FREE_EXTENTS in the job log. One vgextend fixed it. Failback also overwrites the source: anything written there after the last image sync is lost.

Step 5 · Check yourself

Four questions

What does RMM copy onto the target so that the target can pull from the source?

Show the answer

RMM logs into the target as root and copies its own private key onto it. Take that to your security review. What you control is the lifetime of the RMM, the network it sits on, and how quickly it is destroyed after a migration wave.

Does RackWare publish a recovery point or recovery time figure?

Show the answer

RackWare publishes no RPO or RTO number anywhere. The figures in this unit are measurements from test runs, each with the conditions it states.

Pilot Light onto a ROVS DR cluster, with the RMM outside that cluster. What happened on RMM 7.7.4.19?

Show the answer

Plan on Hot or Warm targets, both running, for a ROVS DR site. Pilot Light did work onto a VPC virtual server, for Linux and Windows, from an RMM anywhere that reaches the subnet.

Review question from Unit 6.1. Northgate has a physical server. Can MTV migrate it?

Show the answer

MTV reaches vSphere and nothing else. That is the gap RMM fills.
