Unit 2 of Module 3

Pod network, localnet or Layer 2?

By the end you can pick a network for a VM from a stated need, and say what that choice costs.

About 10 minutesNo cluster needed5 steps

Northgate Freight is moving off vSphere. The company is made up; the output in this unit is real. Its VMs have different needs, and they will not all go on the same network.

Every statement and output in this unit comes from tutorial chapters 20, 21, 24, 26, 32 and 37, apart from the review question, which comes from chapter 06. The VMware comparisons are rough mappings, not IBM statements.

Step 1 · Predict

Three places to attach a VM

The pod network is the default for every pod and VM. Localnet and Layer 2 are extra networks, called secondary, that you define with a cluster network resource (a CUDN).

There is a third kind of CUDN, Layer 3, which gives each node its own subnet. Is it a good fit for a VM?

Show the answer

Red Hat states that OpenShift Virtualization only supports the Layer 2 and Localnet topologies. The address on a Layer 3 network comes from the subnet of the worker the VM runs on, so a VM that live-migrates lands in a different subnet and needs a new address.

Step 2 · Run it

Why localnet and Layer 2 have different packet sizes

Run each command in turn. The output is what a ROVS cluster returned.

bash
oc get network.operator.openshift.io cluster -o jsonpath='{.spec.defaultNetwork.ovnKubernetesConfig.mtu}'
8900

8900 for the overlay. The worker interfaces are 9000.

The 100-byte gap is the Geneve header.

Each CUDN makes a network attachment definition (NAD). Which kind of CUDN has a NAD that names an mtu of 9000?

Show the answer

The localnet NAD names an mtu of 9000. The Layer 2 NAD has no mtu key. The next two commands show both.

oc get net-attach-def scratch-w3c-ln -n scratch-w3c-net -o jsonpath='{.spec.config}'
{"cniVersion":"1.1.0","mtu":9000,"name":"cluster_udn_scratch-w3c-ln",
 "netAttachDefName":"scratch-w3c-net/scratch-w3c-ln","physicalNetworkName":"vpc-vlans",
 "role":"secondary","topology":"localnet","type":"ovn-k8s-cni-overlay","vlanID":360}

Localnet: mtu 9000, written out.

It is bridged onto the 9000-byte underlay, so it pays no overlay tax.

oc get net-attach-def scratch-w3c-l2 -n scratch-w3c-net -o jsonpath='{.spec.config}'
{"cniVersion":"1.1.0","name":"cluster_udn_scratch-w3c-l2",
 "netAttachDefName":"scratch-w3c-net/scratch-w3c-l2","role":"secondary",
 "topology":"layer2","type":"ovn-k8s-cni-overlay"}

Layer 2: no mtu key at all.

An omitted mtu inherits the cluster value. A CentOS guest on one came up at 8900.

Step 3 · Design it

Pick a network for each need

Choose one, then open the worked answer. The answers come from chapters 21, 24, 26 and 37.

Need A. Northgate's VMs need real VPC subnet addresses that other VPC resources reach directly.

Show the worked answer

Localnet. The VM gets a real VPC subnet address, and inherits VPC routing, Transit Gateway and Direct Link. A VM migrated onto it gets a new address: MTV's Preserve static IPs does not work with localnet. It is the closest match to a VLAN-backed port group on a vDS. The cost: no NetworkPolicy on that interface, and one zone only.

Need B. A tier of VMs must talk to each other across workers on their own address range. It needs no connection to the outside.

Show the worked answer

Layer 2, secondary. It is a Geneve overlay across all nodes. It needs no OVS bridge, no VNI and no VPC resource, and it has no outside path unless you add a router. The cost: no outside path is not the same as filtered. A NetworkPolicy does not stop VMs on it from talking to each other.

Need C. A new application VM needs an ordinary NetworkPolicy on its main interface. It needs no static IP and no VPC address.

Show the worked answer

The pod network. A NetworkPolicy polices a pod's primary network, and the default pod network is one. A primary Layer 2 or Layer 3 network replaces it and is policed the same way. A secondary interface is not covered by it.

Need D. Migrated VMs must keep their vSphere addresses and need in-cluster NetworkPolicy on those interfaces. Which one network gives both?

Show the worked answer

A primary Layer 2 network. It is the only network MTV's Preserve static IPs works on, and a primary network is policed by NetworkPolicy. The conditions: the source VM is powered on and runs a VMware guest agent. You cannot set addresses yourself on a primary network, and localnet and secondary networks do not keep migrated addresses. Decide this before the migration plan.

Step 4 · Spot the fault

Three failures that look alike

A VM on a Layer 2 segment cannot reach another VM. What each symptom means, from chapter 32.

curl hangs, then exits with code 28 (Ncat: TIMEOUT. with ncat). What does that tell you?

Show the answer

A hang is a drop: a policy, a firewall or a black-holed route. Destination Host Unreachable with ip neigh showing FAILED is different: ARP got no reply, so nothing holds the address. A missing or stopped router pod looks like that.

The test prints Connection refused. A colleague writes "the segment is isolated". Is that right?

Show the answerRefused is not blocked.

Refused means the path works end to end and nothing is listening on that port. It is not enforcement. Reading it as proof of isolation is the most common way a segmentation statement turns out to be false.

Step 5 · Check yourself

Three questions

Review question from Unit 1.3. Northgate wants to live migrate VMs to any worker and to use VNIs. Which layout?

Show the answer

In a single zone, live migration can go to any worker and VNI networking is simple. In three zones, live migration stays inside one zone and each VNI is tied to one zone.

Northgate wants a different pod network range after the cluster is ordered. Can it change?

Show the answer

Neither the pod range nor the service range can be changed after the cluster is created, and four 172.x ranges are prohibited. Read yours off the cluster. On one ROVS cluster the pod range was 172.17.0.0/17, but another cluster ran 172.23.0.0/17.

A VM's only interface is on a secondary Layer 2 network. Can it use the cluster's DNS service?

Show the answer

The cluster DNS address lives in the service network, which nothing on the overlay can route to. Pointing such a VM at it gives resolution timeouts that look like a routing fault.
