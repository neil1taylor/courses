Unit 2 of Module 5

Updates and node maintenance

By the end you can say who updates what on ROVS, drain a worker safely before it is reloaded, and say what a drain does to each kind of VM.

About 10 minutesNo cluster needed5 steps

Northgate Freight is a made-up company. Its admins plan ESXi patching around maintenance mode. On ROVS, IBM patches the platform, and the timing of each worker reload is yours.

Every command, output and fact in this unit comes from real runs on lab clusters. The review question repeats one from unit 2.2.

Step 1 · Predict

Who updates what

ROVS runs on ROKS, so IBM manages more than you would on a self-managed OpenShift cluster. Pick the owner of each part.

Who updates the control plane, and what does it do to your VMs?

Show the answer

IBM updates the API server, etcd and controllers on a regular schedule. The control plane is highly available, and VMs run on workers, not on control plane nodes.

A patch update for the virtualization operators is coming. What do you do?

Show the answer

The openshift-virtualization add-on owns the virtualization, NMState and Node Maintenance operators. Patches apply on the stable channel with automatic approval. Editing its subscriptions or approving its install plans by hand is at best pointless. Minor upgrades are a command against the add-on, after the cluster is upgraded first.

Which command applies a fix pack to a bare metal worker?

Show the answer

worker update refused a ROVS worker, and its advice was to delete the worker. worker reload applied the pending fix pack. replace deletes the worker and provisions a new one. ODF is yours to update too, as an add-on update. It restarts storage daemons, so plan it like a reload.

From vSphere: IBM does roughly what vCenter upgrades and ESXi patching do. The add-on is the counterpart of Update Manager, but IBM runs it. A rough mapping, not an IBM statement.

Step 2 · Explore the parts

Drain a worker before it is reloaded

These four commands worked on ROVS. Select a part of the drawing to see what it does and which line defines it. You can also click a line.

↑ tap any box

Cordon

Marks the node unschedulable, so no new VM lands on it. After the cordon, oc get node showed Ready,SchedulingDisabled.

From vSphere: cordon plus drain is roughly putting an ESXi host into maintenance mode, and uncordon is leaving it. A rough mapping, not an IBM statement.

Drain

Evicts the pods. The selector limits it to the VMs' launcher pods. A VM whose eviction strategy is LiveMigrate is live-migrated. A VM with None is shut down. In a later run this drain moved seven running VMs off a worker in 54 seconds, every migration Succeeded, and no VM stopped.

Watch for this. A reload does not wait for live migrations. A fix-pack reload of a worker running nine live-migratable VMs stopped all nine with the worker, and no migration completed. The protected DR test VM was down for 32 minutes.

Check

Nothing should be left on the node. In a by-hand drain of a worker that held 13 VMs, this listing returned nothing, because the VMs had moved. The drain took 3 minutes 23 seconds.

Reload

A reload reimages the worker and reinstalls it with the latest patch version. It is not a reboot: the node's ODF disks were kept in all three measured reloads, but its OSDs were offline for 26 to 70 minutes, with Ceph on two copies. Reload one worker at a time and wait for HEALTH_OK between them. Two at once on a three-worker cluster leaves one copy, and VMs hang.

From vSphere: rolling worker updates are roughly like rolling ESXi upgrades with DRS fully automated. A rough mapping, not an IBM statement.

oc adm cordon <node>
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data --pod-selector=kubevirt.io=virt-launcher
oc get vmi -A -o wide | grep <node>        # nothing left
ibmcloud ks worker reload --worker <worker-id>
Step 3 · Predict, then run it

Ask what a drain would do, without draining

A drain is only one call to the eviction API per pod. You can make that call yourself, against your own VM, instead of draining a node that carries other people's VMs.

bash

# the cluster-wide default for a VM that sets no eviction strategy

oc get hyperconverged kubevirt-hyperconverged -n openshift-cnv -o jsonpath='{.spec.evictionStrategy}'
LiveMigrate

That was the value on the lab cluster, because someone had set it. A second, untouched ROVS cluster read None, and a drain destroyed and recreated its VM with no migration. Read yours.

The next call evicts the VM's launcher pod. It will be refused. Is that good news or bad?

Show the answerRead the message, not just the refusal.

Two of the three possible results are refusals, and they mean opposite things. "Eviction triggered evacuation" means a drain would live-migrate the VM. "Is configured with an eviction strategy but is not live-migratable" means the drain would not finish. An allowed call would power the VM off.

# one eviction call; $POD is the VM's virt-launcher pod

oc create --raw "/api/v1/namespaces/$(oc project -q)/pods/$POD/eviction" -f evict.json
Error from server: admission webhook "virt-launcher-eviction-interceptor.kubevirt.io"
denied the request: Eviction triggered evacuation of VMI "scratch-w2c-mig/scratch-w2c-vm-virt"

The refusal is the success case. KubeVirt set the evacuation field on the VMI and created an evacuation migration.

# the VMI, as the migration ran and after it finished

oc get vmi scratch-w2c-vm-virt -o custom-columns=UID:.metadata.uid,PHASE:.status.phase,NODE:.status.nodeName,EVAC:.status.evacuationNodeName
UID                          PHASE     NODE           EVAC
678a770a-...-0f30c504bc1b   Running   ...-00000167   ...-00000167
678a770a-...-0f30c504bc1b   Running   ...-0000039f   <none>

Same UID, still Running, different node. The field clears once the VM has landed elsewhere.

Watch for this. The eviction path was run. A drain of a shared node was not, for this probe.

Step 4 · Spot the fault

The drain that does not finish

A VM has a 1Gi RWO disk and evictionStrategy: LiveMigrate. This is the probe, on OpenShift 4.21.27, in a scratch namespace.

$ oc get vmi scratch-drainprobe-rwo -o jsonpath='{range .status.conditions[*]}{.type}={.status} reason={.reason}{"\n"}{end}'
Ready=True reason=
DataVolumesReady=True reason=AllDVsReady
LiveMigratable=False reason=DisksNotLiveMigratable

$ oc create --raw "/api/v1/namespaces/scratch-drainprobe/pods/$POD/eviction" -f evict.json
Error from server: admission webhook "virt-launcher-eviction-interceptor.kubevirt.io" denied
the request: VMI scratch-drainprobe-rwo is configured with an eviction strategy but is not
live-migratable

IBM drains the worker for its own update. What happens to this VM and to the drain?

Show the answerA forgotten RWO disk blocks the platform's maintenance, not just yours.

The launcher pod stayed Running, the VMI stayed on the same node, and oc get vmim showed no migration object at all. The node does not empty and stays cordoned until you step in.

With LiveMigrateIfPossible the same call returns "status":"Success","code":201. What does that setting trade away?

Show the answer

A VM that can migrate still migrates. One that cannot is shut down and restarted by its runStrategy, so the drain completes. Know which VMs those are: oc get vmi -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,LM:'.status.conditions[?(@.type=="LiveMigratable")].status'.

A worker dies at 02:00 and a VM with runStrategy: Always ran on it. By default on ROVS, what happens?

Show the answer

Red Hat says a VM with runStrategy: Always is not automatically relocated when machine health checks are not deployed. ROVS does not serve the Machine API, so out of the box nothing removes the Node object. When one worker was rebooted twice, the VM restarted only after the node came back, with outages of 213 and 229 seconds. A worker that stays down could not be reproduced, because IBM gives a ROVS customer no way to power one off.

Step 5 · Check yourself

Four questions

You start a fix-pack reload on a worker that runs live-migratable VMs, and you have not drained it. What did the measured run show?

Show the answer

The reload does not wait for live migrations. Drain the worker yourself first, and check that no VM is left on it.

A VM sets no evictionStrategy. What does a drain do to it?

Show the answer

The VM inherits the HyperConverged setting. Read your cluster's value rather than assuming either result. Set it on the VM to own the behaviour.

How many workers do you reload at once?

Show the answer

There is no MachineConfigPool on ROVS to set a limit for you. You pace the reloads yourself. Two at once on a three-worker cluster leaves one copy.

Review from unit 2.2. Why is a three-node cluster a lab configuration?

Show the answer

Three nodes can hold three copies. The risk is losing two at once. IBM's guidance for production clusters running three copies is to start with six nodes.
