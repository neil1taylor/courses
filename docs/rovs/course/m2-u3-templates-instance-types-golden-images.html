Unit 3 of Module 2

Templates, instance types and golden images

By the end you can say what a template, an instance type, a preference and a DataSource each hold, and how a golden image is built, sealed and cloned.

About 10 minutesNo cluster needed5 steps

Northgate Freight is a made-up company. It wants every new VM to start the same way, without anyone rebuilding the same disk by hand. This unit shows how, with real output.

Every definition, command and output in this unit comes from real runs on test clusters.

Step 1 · Explore the parts

One VM, built from shared pieces

VMware bundles hardware, disk image and customisation into one template. OpenShift Virtualization separates them. Select a part of the drawing to see what it is and which lines define it. You can also click a line.

↑ tap any box

Compute: the instance type

A reusable compute profile. The VM names it instead of writing CPU and memory. Here custom.db-large is 8 vCPUs and 32Gi.

From vSphere: the CPU and memory settings you keep in a template.

Watch for this. u1.medium is one vCPU with 4Gi, not two.

OS defaults: the preference

OS-specific defaults such as disk bus, NIC model, boot order and machine type. centos.stream9 is one the cluster ships.

From vSphere: roughly the disk bus and tools settings of Guest OS Customization.

Watch for this. A preference sets device defaults, not a network. In one test a Windows VM with no network entries started with no network interface at all.

Image: the DataSource

A pointer to the golden image. A DataSource holds no data. The built-in ones live in the openshift-virtualization-os-images namespace.

From vSphere: a template in a content library. That namespace plays the content library.

Boot disk

The VM's own volume, cloned from the image. This definition names the virtualization storage class, ReadWriteMany and Block.

Watch for this. Name the class in every definition you standardise. The shipped templates name none and still landed on the right class, but your manifests are the ones that get copied and inherited.

Own settings

Disks, network card and guest setup stay in the VM, because they belong to this VM and not to a compute profile.

apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: db-server
  namespace: my-project
spec:
  instancetype:
    name: custom.db-large
    kind: VirtualMachineClusterInstancetype
  preference:
    name: centos.stream9
    kind: VirtualMachineClusterPreference
  runStrategy: Always
  dataVolumeTemplates:
  - metadata:
      name: db-server
    spec:
      sourceRef:
        kind: DataSource
        name: centos-stream9
        namespace: openshift-virtualization-os-images
      storage:
        storageClassName: ocs-storagecluster-ceph-rbd-virtualization
        accessModes:
          - ReadWriteMany
        volumeMode: Block
        resources:
          requests:
            storage: 100Gi
  template:
    spec:
      domain:
        devices:
          interfaces:
          - name: default
            masquerade: {}
          rng: {}
      networks:
      - name: default
        pod: {}
      volumes:
      - dataVolume:
          name: db-server
        name: rootdisk
      - cloudInitNoCloud:
          userData: |
            #cloud-config
            user: centos
            password: my-password
            chpasswd: { expire: False }
        name: cloudinitdisk
Step 2 · Run it

Make a VM from a shipped template

Run each command in turn. The output is what the test cluster returned.

bash
oc process centos-stream9-server-small -n openshift \
  -p NAME=my-centos-vm | oc apply -f - -n my-project
(the chapter records no output for this command)

oc process fills in the template's parameters and prints a VM definition.

Forty seconds after that command: is the VM running?

Show the answer

The Red Hat templates ship runStrategy: Halted. The console wizard flips it for you. On the command line nothing flips it, so you start the VM yourself.

oc get vm,dv,pvc -n my-project
NAME                                      AGE   STATUS    READY
virtualmachine.kubevirt.io/my-centos-vm   40s   Stopped   False

NAME                                      PHASE       PROGRESS
datavolume.cdi.kubevirt.io/my-centos-vm   Succeeded   100.0%

The disk is fully provisioned. The VM is not running.

oc get vm my-centos-vm -n my-project -o jsonpath='{.spec.runStrategy}'
Halted

Start it with virtctl start my-centos-vm -n my-project.

oc get template centos-stream9-server-small -n openshift \
    -o jsonpath='{range .parameters[*]}{.name}{"\n"}{end}'
NAME
DATA_SOURCE_NAME
DATA_SOURCE_NAMESPACE
CLOUD_USER_PASSWORD

Four parameters. There is no NAMESPACE. Choose the project with -n on oc apply.

Predict: how many vCPUs and how much memory does the instance type u1.medium give a VM?

Show the answerMemory grows faster than CPU.

On the cluster checked: u1.nano 1 vCPU 512Mi, u1.micro 1 vCPU 1Gi, u1.small 1 vCPU 2Gi, u1.medium 1 vCPU 4Gi, u1.large 2 vCPUs 8Gi, u1.xlarge 4 vCPUs 16Gi, u1.2xlarge 8 vCPUs 32Gi. Up to u1.large the series scales memory faster than CPU.

Step 3 · Explore the parts

How a golden image reaches a VM

A golden image is a pre-configured, sealed OS disk. Every VM built from it gets a private clone, so changes in one VM never touch another.

From vSphere: a DataImportCron is a subscribed content library with automatic sync. The golden image is a content library item. Deploying from it is deploy from template.

bash
oc get storageprofile ocs-storagecluster-ceph-rbd-virtualization \
  -o jsonpath='{.status.cloneStrategy}{"  "}{.status.dataImportCronSourceFormat}{"\n"}'
csi-clone  snapshot

csi-clone: the storage layer makes the copy. On this class it is close to instant.

snapshot: golden disks made by a DataImportCron are stored as snapshots.

oc get datasource centos-stream9 -n openshift-virtualization-os-images -o jsonpath='{.spec.source}'
{"snapshot":{"name":"centos-stream9-80f964c34dc8","namespace":"openshift-virtualization-os-images"}}

The shipped DataSource points at a snapshot. It holds no data itself.

Watch for this. A running VM is unaffected when its golden image updates, because it has its own clone. Only VMs created after the update get the new image.

Step 4 · Spot the fault

The seal that undid itself

Sealing strips a disk's machine identity, so clones do not share an SSH host key or machine ID. The builder ended the seal with poweroff in the guest, on a VM with runStrategy: Always. This is the real output.

$ oc get vmi my-vm -o jsonpath='{.metadata.uid}'
1474340b-6138-4285-b1ac-39b32e293825

$ virtctl -n my-project ssh centos@vm/my-vm -c 'sudo poweroff'

# 15 seconds later
$ oc get vm,vmi my-vm
my-vm   Running   True
$ oc get vmi my-vm -o jsonpath='{.metadata.uid}'
aef84207-8abd-493c-8b7a-1cacb0f36ea7      <-- a different VMI

The VM is running again, with a different VMI. What went wrong?

Show the answer

With runStrategy: Always, a guest poweroff deletes the VMI and the controller creates a new one at once. That boot regenerates the SSH host keys and the machine ID that were just deleted. The VM looks fine and the image is not sealed.

How do you make the seal stick?

Show the answer

Build the golden image with runStrategy: Manual, so a guest poweroff sticks. End the seal with virtctl stop from outside, which sets runStrategy: Halted first. A reboot regenerates exactly the identity you just removed.

Step 5 · Check yourself

Four questions

Which object holds the CPU and memory a VM refers to by name?

Show the answer

The instance type is the reusable compute profile. The preference holds OS-specific defaults. The DataSource points at the disk image.

Where does Northgate create its own golden images?

Show the answer

openshift-virtualization-os-images is managed content. The operator reconciles it, and resources added there may be reverted or replaced on an update with no warning. Reading from it is fine. Writing into it is what gets reverted.

You run oc process on a shipped template and apply the result. What state is the VM in?

Show the answer

The VM is created with runStrategy: Halted, and its disk is provisioned. Start it with virtctl start.

Review from unit 2.2. Which storage class does every VM disk use?

Show the answer

The virtualization class. Name it, with ReadWriteMany and Block, in every definition you standardise, so every VM built from a template or golden image carries it.
