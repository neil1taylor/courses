Unit 1 of Module 5

Live migration

By the end of this unit you'll be able to read what a live migration reports, say what a VM keeps and what it loses when it moves, and say what has to be true for a migration to run.

About 10 minutesNo cluster needed5 steps

Northgate Freight is a made-up haulier that's moving off vSphere. Its admins know vMotion. On ROVS a live migration is an object you can read, and a few conditions decide whether it runs.

Every command, output and fact in this unit comes from a real run on a test cluster. The review question repeats one from unit 2.2.

Step 1 · Explore the parts

What a migration reports

This is the migration state of one VM after it moved. Tap a part of the drawing to see what it says and which lines define it. You can also click a line.

↑ tap any box

Result

The migration is completed and its mode is PreCopy, which means memory pages are copied while the VM keeps running, and then a final switchover moves execution to the new node. A 2 GiB idle Fedora guest switched over in about one second. How long a migration takes depends on the VM's memory size, how fast it writes to memory, and the network between the nodes.

From vSphere: it's closest to vMotion. That's a rough match of our own, and IBM doesn't describe it this way.

Nodes

The VM moved from one worker to another. On ROVS a live migration works within a single zone only, and a move across zones needs a shutdown. That comes from IBM's documentation. Our cluster has one zone, so we couldn't run it here.

From vSphere: there's no long-distance vMotion between sites.

Pods

A VM runs inside a virt-launcher pod. A migration starts a new pod on the target node, copies the memory across, then ends the source pod. The VM kept the same VirtualMachineInstance UID and creation time and never left Running, so the guest didn't reboot.

Limits

At most 5 migrations run in the cluster at once and 2 leave any one node. allowAutoConverge and allowPostCopy are both off, so a VM that writes memory faster than the link can copy it times out instead of being forced to finish.

Watch for this. completionTimeoutPerGiB is widely documented as 800, but on this cluster it was 150. Read your own value before you plan a maintenance window around it.

From vSphere: these are the concurrent vMotion limits.

Step 2 · Predict, then run it

Two VMs, two storage classes

There are two Fedora VMs, one on each ODF RBD class, both RWX Block, both on the default pod network. We checked that each one answered on port 22 before anything moved.

bash

# can each VM migrate? LM is LiveMigratable, SLM is StorageLiveMigratable

oc get vmi -n scratch-w2c-mig -o custom-columns=\
NAME:.metadata.name,PHASE:.status.phase,NODE:.status.nodeName,\
LM:'.status.conditions[?(@.type=="LiveMigratable")].status',\
SLM:'.status.conditions[?(@.type=="StorageLiveMigratable")].status'
NAME                     PHASE     NODE            LM     SLM
scratch-w2c-vm-generic   Running   ...-00000167    True   True
scratch-w2c-vm-virt      Running   ...-00000167    True   True

Both conditions are True before anything moves, and both VMs sit on the same worker.

# the VM on ocs-storagecluster-ceph-rbd-virtualization

virtctl migrate scratch-w2c-vm-virt -n scratch-w2c-mig
VM scratch-w2c-vm-virt was scheduled to migrate

The next VM is on the generic class, ocs-storagecluster-ceph-rbd, with an RWX Block disk. Does it migrate?

Show the answerThe generic class migrates too.

Yes, as readily as the first. It's still the wrong class for VMs. IBM hasn't validated it for VM workloads, and the risk is guest data corruption under Windows I/O patterns rather than a stranded VM. Run the command to see it move.

# the VM on ocs-storagecluster-ceph-rbd

virtctl migrate scratch-w2c-vm-generic -n scratch-w2c-mig
VM scratch-w2c-vm-generic was scheduled to migrate

# the migration objects

oc get vmim -n scratch-w2c-mig
NAME                        PHASE       VMI
kubevirt-migrate-vm-c8nrh   Succeeded   scratch-w2c-vm-virt
kubevirt-migrate-vm-vs6cf   Succeeded   scratch-w2c-vm-generic

Both Succeeded, and both moved from worker ...-00000167 to ...-0000039f.

Both kept the same VMI UID and creation time and never left Running, so neither guest rebooted.

You didn't name these objects. kubevirt-migrate-vm-* is a migration you asked for, and kubevirt-evacuation-* is one that KubeVirt started because something tried to evict the launcher pod.

Watch for this. No access mode, migration condition or test migration told the two classes apart, so audit by class name.

Step 3 · Predict

What a client sees

The guest doesn't notice a migration, but its clients might. This VM is on the default pod network, behind a ClusterIP Service.

The VM migrates. What happens to the address its clients use?

Show the answerThe guest didn't change, but its address did.

It changes. The guest didn't reboot and its settings didn't change. The launcher pod on the target is a new pod with a new pod IP, though, and with masquerade binding that pod IP is the VM's reachable address. Nothing in the migration status flags it. A probe holding the old address saw the VM disappear for good.

Through a ClusterIP Service, one migration cost four failed probes out of 229. How long was the VM unreachable?

Show the answer

Roughly 3.6 seconds, while the Service endpoint was reprogrammed. Then it recovered on its own. That's one probe loop, one migration and one guest, so it isn't a figure for your cluster.

Which addresses stay with the VM when it moves?

Show the answer

A localnet or Layer 2 address. A localnet address from the VPC subnet, or a Layer 2 overlay address, follows the VM, and the pod IP doesn't. We don't show a run of either case here. A localnet VM also needs its VLAN attachment at cluster scope, so that the network can float with it.

Step 4 · Predict

A migration that doesn't run

For each of these three symptoms, pick the likely cause.

A migration sits in Scheduling. What do you check?

Show the answer

Node capacity, affinity and zones. There's no suitable target node, because there aren't enough resources, an affinity rule rules the nodes out, or every candidate node is in another zone. Check capacity with oc describe node.

A localnet VM migrates, then loses its connectivity. Why?

Show the answer

Its VLAN attachment is pinned. The attachment exists only on the source worker. Reattach the VNI at cluster scope, with --cluster-id, so that it floats with the VM within the zone.

A migration is cancelled by a timeout. The guest writes memory fast. What can you do?

Show the answer

Reduce the workload, or raise the timeout. Auto-converge and post-copy are both off here, so nothing forces a busy VM to finish. At 150 seconds a GiB, a 64 GiB VM has a budget of roughly 2.7 hours. At the widely quoted 800 it would be about 14 hours.

From vSphere: there's no EVC baseline. Keep VMs that migrate within pools of one bare metal flavour, because a worker with different CPU features can refuse a VM.

Step 5 · Check yourself

Four questions

Which pair of things has to be true for a VM to live migrate?

Show the answer

RWX disks and a worker in the same zone. Only RWX lets the source and destination nodes use the disk at once, and a migration stays within one zone. Either RBD class migrated, but only the virtualization class is validated for VMs.

What does virtctl migrate my-vm create?

Show the answer

A migration object with a generated name. It's a VirtualMachineInstanceMigration, and a follow-up command that assumes a name you chose won't find it. Create the object yourself if you need a predictable name.

A pod-network VM has just migrated and its clients can't reach it. What happened?

Show the answer

Its pod IP changed, and the migration itself was fine. Put a Service in front of the VM, or give it a localnet or Layer 2 address.

Review from unit 2.2. A VM's disk shows RWX. What does that tell you about its storage class?

Show the answer

Nothing. Both RBD classes offer RWX Block, and the storage profile lists it first, so a request for any mode gets RWX Block on either class. Check the class name instead.
